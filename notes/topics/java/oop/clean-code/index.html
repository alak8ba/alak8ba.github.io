    Clean Code • Écrire du code qui se lit

    Le code est lu bien plus souvent qu'il n'est écrit. Le clean code n'est pas une question d'esthétique : c'est ce qui détermine le coût de la prochaine modification.

    Principe

    Une seule question guide tout le reste :

    est-ce qu'un développeur qui découvre ce code comprend son intention sans demander d'explication ?

    1. Nommage

    Le nom doit dire l'intention, pas l'implémentation.

    // A eviter
List<String> l;
int d;                      // durée ? distance ? date ?
void process(Data data);
boolean flag;

// Correct
List<String> referencesEnErreur;
int dureeTraitementMs;
void validerAssure(AssureDto assure);
boolean estEligibleAuRemboursement;
    Élément Convention
    Classe nom, PascalCase • BookingService
    Méthode verbe, camelCase • calculerMontant()
    Booléen est..., a..., peut... • estValide
    Constante UPPER_SNAKE_CASE
    Collection pluriel • assures, pas assureList

    Un nom long et clair vaut mieux qu'un nom court et ambigu. Si un nom est difficile à trouver, c'est souvent la responsabilité de la classe qui est floue.

    2. Fonctions

    • courtes • si elle ne tient pas sur un écran, elle fait plusieurs choses
    • un seul niveau d'abstraction • ne pas mélanger règle métier et manipulation de chaînes
    • peu de paramètres • au-delà de trois, introduire un objet
    • pas de paramètre booléen • il signale deux comportements dans une seule méthode
    // A eviter : le booléen cache deux traitements
public void enregistrer(Assure assure, boolean notifier) { ... }

// Correct : deux méthodes explicites
public void enregistrer(Assure assure) { ... }
public void enregistrerEtNotifier(Assure assure) { ... }

    Extraire pour nommer

    // Avant : la condition demande un effort de lecture
if (assure.getAge() >= 18 && assure.getContrat() != null
        && assure.getContrat().getStatut() == ACTIF) { ... }

// Après : le nom porte la règle métier
if (estEligible(assure)) { ... }

private boolean estEligible(Assure assure) {
    return assure.getAge() >= 18
        && assure.getContrat() != null
        && assure.getContrat().getStatut() == ACTIF;
}

    Extraire une méthode, c'est surtout donner un nom à une intention.

    3. Commentaires

    Le code dit ce qui est fait, le commentaire dit pourquoi.

    // Commentaire inutile : paraphrase du code
// incrémente le compteur
compteur++;

// Commentaire utile : explique une décision non évidente
// Le partenaire renvoie 200 avec un corps vide en cas de timeout interne.
// On traite ce cas comme un échec pour éviter un double prélèvement.
if (reponse.getBody() == null) {
    throw new TechnicalException("Réponse vide du partenaire");
}

    Un commentaire qui explique un code obscur est souvent le signe qu'il faut renommer ou extraire. Et un commentaire faux est pire que pas de commentaire : le code évolue, le commentaire ment.

    4. DRY, KISS, YAGNI

    Principe Signification Piège
    DRY • Don't Repeat Yourself une règle métier, un seul endroit factoriser deux codes qui se ressemblent par hasard crée un couplage artificiel
    KISS • Keep It Simple la solution la plus simple qui marche l'abstraction prématurée coûte plus qu'elle ne rapporte
    YAGNI • You Aren't Gonna Need It ne pas coder pour un besoin hypothétique « on en aura besoin plus tard » est presque toujours faux

    DRY s'applique à la connaissance métier, pas aux lignes de code identiques.

    5. Gestion des erreurs et des absences

    // A eviter : le null se propage et explose plus loin
public Assure trouver(String ref) {
    return repository.findByRef(ref); // null si absent
}

// Correct : l'absence est explicite dans la signature
public Optional<Assure> trouver(String ref) { ... }

// Ou : l'absence est une erreur métier
public Assure trouverOuEchouer(String ref) {
    return repository.findByRef(ref)
            .orElseThrow(() -> new AssureNotFoundException(ref));
}

    Une exception plutôt qu'un code retour, un Optional plutôt qu'un null, et jamais de catch vide.

    6. Code smells à savoir nommer

    Smell Description Correction
    God class une classe qui sait tout faire découper par responsabilité (SRP)
    Long method méthode de 200 lignes extraire des méthodes nommées
    Duplicated code même règle à trois endroits factoriser
    Magic number if (statut == 3) constante ou enum nommés
    Long parameter list 7 paramètres objet paramètre
    Feature envy une classe manipule surtout les données d'une autre déplacer le comportement vers la donnée
    Primitive obsession String iban partout type dédié Iban avec sa validation
    Dead code code commenté ou jamais appelé supprimer • Git garde l'historique

    7. Boy Scout Rule

    Laisser le code un peu plus propre qu'on ne l'a trouvé.

    Concrètement : au passage sur un fichier, renommer une variable obscure, extraire une méthode, supprimer du code mort. Un refactoring continu et petit évite le « grand refactoring » qui n'arrive jamais.

    La condition pour refactorer sans peur : des tests. Sans filet, on ne touche à rien • c'est ce qui transforme un code sale en code figé.

    8. Lien avec SOLID et la testabilité

    Clean code et testabilité sont la même chose vue sous deux angles :

    • une classe difficile à tester a trop de responsabilités (SRP)
    • une classe qui fait new sur ses dépendances est intestable (DIP)
    • une méthode qui demande dix mocks fait trop de choses

    La difficulté à écrire un test est un signal de conception, pas un problème de test.

    Points d'attention

    • confondre clean code et sur-ingénierie • trois couches d'abstraction pour un CRUD, ce n'est pas propre
    • factoriser trop tôt, avant que la règle commune soit avérée
    • laisser du code commenté « au cas où »
    • nommer en fonction du type (assureList) plutôt que du rôle
    • refactorer sans tests

    Questions classiques

    C'est quoi du code propre ?

    Du code dont l'intention se lit sans explication : noms parlants, fonctions courtes à responsabilité unique, erreurs traitées explicitement, testable.

    DRY, KISS, YAGNI ?

    Ne pas dupliquer la connaissance métier • garder la solution simple • ne pas coder un besoin hypothétique.

    Faut-il commenter son code ?

    On commente le pourquoi (décision, contournement, contrainte externe), pas le quoi • si le quoi a besoin d'un commentaire, il faut renommer ou extraire.

    Quel lien entre clean code et tests ?

    Un code difficile à tester est un code mal découpé • la testabilité est un révélateur de la qualité de conception.

    Comment traiter du code legacy sale ?

    Le couvrir de tests de caractérisation d'abord, refactorer ensuite, par petites touches (Boy Scout Rule).

    Synthèse

    • le nom porte l'intention • fonctions courtes, un seul niveau d'abstraction
    • commenter le pourquoi, jamais le quoi
    • DRY sur la connaissance métier, KISS et YAGNI contre la sur-ingénierie
    • Optional et exceptions plutôt que null et codes retour
    • savoir nommer les code smells • c'est ce qui permet d'en parler en revue
    • pas de refactoring sans tests
