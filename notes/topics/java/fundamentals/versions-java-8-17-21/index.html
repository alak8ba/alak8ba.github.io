    Java 8, 17, 21 • ce qui change et ce qui coûte

    Contexte

    C'est la comparaison la plus fréquemment posée sur un projet, parce qu'elle recouvre deux sujets distincts : ce que le langage moderne apporte, et ce qu'une migration coûte réellement - c'est-à-dire ce qui casse.

    Version Sortie Support (Oracle / OpenJDK) Statut de fait
    Java 8 2014 LTS, encore maintenu omniprésent en legacy, plus un choix
    Java 11 2018 LTS palier de migration classique depuis 8
    Java 17 2021 LTS socle de Spring Boot 3 - minimum requis
    Java 21 2023 LTS cible actuelle des nouveaux projets
    Java 25 2025 LTS prochain palier, adoption en cours

    Depuis Java 9, une version sort tous les six mois, et une LTS tous les deux ans. Les versions intermédiaires servent à livrer des fonctionnalités en preview ; on ne les met pas en production.

    Java 8 • le socle dont tout le monde parle encore

    // Lambdas et interfaces fonctionnelles
Runnable r = () -> System.out.println("exécuté");

// Streams
List<String> noms = clients.stream()
    .filter(c -> c.isActif())
    .map(Client::getNom)
    .sorted()
    .collect(Collectors.toList());   // toList() en Java 16+

// Optional : rendre l'absence explicite
Optional<Client> trouve = repository.findById(id);
String nom = trouve.map(Client::getNom).orElse("inconnu");

// API date/heure enfin correcte
LocalDate echeance = LocalDate.now().plusDays(30);

// Méthodes par défaut dans les interfaces
interface Notifieur {
    default void notifier(String msg) { log.info(msg); }
}

    Java 8 a introduit le style fonctionnel, Optional, java.time et les méthodes par défaut. Tout ce qui suit est cumulatif : ces acquis restent valables.

    Java 9 à 16 • les apports qui comptent au quotidien

    Version Apport marquant
    9 JPMS (modules), List.of() / Map.of(), Stream.takeWhile
    10 var - inférence de type sur les variables locales
    11 HttpClient standard, String.strip(), isBlank(), lines(), exécution directe d'un .java
    14 messages de NullPointerException utiles (helpful NPE)
    15 text blocks (""")
    16 Stream.toList(), record en preview 
    // var : le type reste statique, il est seulement inféré
var factures = new ArrayList<Facture>();

// Text block : plus de concaténation de SQL ou de JSON
String requete = """
    SELECT f.id, f.montant
      FROM facture f
     WHERE f.statut = 'EMISE'
    """;

// HttpClient (Java 11) : plus besoin d'une librairie tierce pour un appel simple
HttpResponse<String> reponse = HttpClient.newHttpClient()
    .send(HttpRequest.newBuilder(URI.create(url)).build(),

    Java 17 • le socle moderne

    record • les données immuables sans le bruit

    // Avant : ~60 lignes avec getters, equals, hashCode, toString
public record LigneFacture(String reference, int quantite, BigDecimal prixUnitaire) {

    // compact constructor : les invariants restent possibles
    public LigneFacture {
        if (quantite <= 0) throw new IllegalArgumentException("quantité invalide");
    }

    public BigDecimal total() {
        return prixUnitaire.multiply(BigDecimal.valueOf(quantite));
    }
}

    Un record est final, ses champs sont final, equals / hashCode / toString sont générés. Usage naturel : DTO, value objects du domaine, résultats de requête, événements.

    Record et JPA ne se marient pas

    Une entité JPA a besoin d'un constructeur sans argument et de champs mutables : un record ne peut pas être une @Entity. En revanche il est parfait comme projection de lecture (interface-based ou constructor projection) et comme objet du domaine dans une architecture hexagonale, l'entité JPA restant dans l'adapter. → Hexagonal Architecture

    sealed • hiérarchies fermées

    public sealed interface EvenementPaiement
        permits PaiementAutorise, PaiementRefuse, PaiementExpire { }

// Le compilateur sait que la liste est exhaustive :
String libelle = switch (evenement) {
    case PaiementAutorise a -> "autorisé " + a.montant();
    case PaiementRefuse r   -> "refusé : " + r.motif();
    case PaiementExpire e   -> "expiré";
    // pas de default nécessaire - et l'ajout d'un cas casse la compilation
};

    C'est l'outil qui remplace proprement un enum + switch fragile, ou une hiérarchie ouverte où l'on oubliait un cas.

    Switch expression et pattern matching pour instanceof

    // switch qui retourne une valeur, sans fall-through
int jours = switch (statut) {
    case EMISE, RELANCEE -> 30;
    case PAYEE -> 0;
    case LITIGE -> { var d = calculer(); yield d; }
};

// instanceof avec liaison de variable : plus de cast redondant
if (objet instanceof Facture f && f.montant().signum() > 0) {
    traiter(f);
}

    Le reste

    • NPE explicites - le message indique quelle variable était nulle
    • G1 par défaut, ZGC disponible en production (pauses inférieures à la milliseconde)
    • API Random améliorée, Stream.mapMulti
    • encapsulation forte du JDK : l'accès par réflexion aux internes est refusé par défaut

    Java 21 • la version qui change l'architecture

    Threads virtuels • l'apport majeur

    // Avant : un pool borné, parce qu'un thread OS coûte ~1 Mo de pile
ExecutorService pool = Executors.newFixedThreadPool(200);

// Java 21 : un thread virtuel par tâche, des centaines de milliers possibles
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var facture : factures) {
        executor.submit(() -> appelerServiceExterne(facture));  // code bloquant, assumé
    }
}

    Le modèle change : un thread virtuel bloqué sur une entrée/sortie libère son thread porteur. On peut donc revenir à du code séquentiel lisible là où il fallait passer en réactif pour tenir la charge.

    Les deux pièges des threads virtuels

    • un bloc synchronized autour d'une opération bloquante épingle (pin) le thread porteur : remplacer par ReentrantLock sur les sections concernées
    • inutile pour du calcul CPU : les threads virtuels servent aux tâches bloquantes d'entrée/sortie ; pour le CPU, le parallélisme reste borné par le nombre de cœurs

    Côté Spring Boot 3.2+, l'activation tient en une ligne : spring.threads.virtual.enabled=true.

    Pattern matching pour switch et record patterns

    String description = switch (evenement) {
    case PaiementAutorise(var id, var montant) when montant.compareTo(SEUIL) > 0
        -> "gros paiement " + id;
    case PaiementAutorise(var id, var montant)
        -> "paiement " + id;
    case PaiementRefuse(_, String motif)
        -> "refus : " + motif;
    case null
        -> "événement absent";
};

    Le déconstruction de record (record pattern) évite la cascade instanceof + cast + getters.

    Sequenced Collections

    // Une API commune pour « premier » et « dernier », enfin
SequencedCollection<String> liste = new ArrayList<>(List.of("a", "b", "c"));
liste.getFirst();      // au lieu de get(0)
liste.getLast();       // au lieu de get(size() - 1)
liste.reversed();      // vue inversée, sans copie

    Le reste

    • structured concurrency et scoped values (preview en 21, stabilisés ensuite)
    • String templates (preview), génériques sur les patterns
    • performances GC et démarrage améliorées à chaque version

    Migrer • ce qui casse réellement

    C'est la partie qui distingue une réponse théorique d'un vécu.

    Obstacle Version concernée Symptôme Traitement
    Suppression de javax.xml.bind, java.activation, CORBA 11 ClassNotFoundException au démarrage ajouter les artefacts Jakarta en dépendance explicite
    Encapsulation forte du JDK 16 / 17 InaccessibleObjectException (réflexion sur les internes) --add-opens en dépannage, mise à jour de la librairie en solution
    sun.misc.Unsafe, accès aux internes 17+ avertissements puis erreurs remplacer par les API standard (VarHandle)
    Librairies de bytecode obsolètes toutes ASM, Lombok, Mockito, ByteBuddy en échec sur une nouvelle version de classe monter les versions avant de changer de JDK
    SecurityManager déprécié 17 avertissements, suppression annoncée supprimer l'usage
    Changement de GC par défaut et de heap ergonomics 9+ consommation mémoire différente en conteneur fixer explicitement -XX:MaxRAMPercentage
    Format des dates CLDR 9 libellés de dates modifiés dans les exports figer la Locale, tester les formats
    JPMS 9 split packages, modules automatiques rester sur le classpath, sauf besoin réel de modularisation

    L'ordre de migration qui fonctionne

    1. monter les dépendances sur la dernière version compatible avec le JDK actuel
    2. compiler avec le nouveau JDK en gardant --release 8 ou 11 - cela isole les erreurs de compilation des erreurs d'exécution
    3. exécuter les tests avec le nouveau JDK, traiter les InaccessibleObjectException
    4. puis monter --release et adopter la nouvelle syntaxe
    5. relever les paramètres GC / mémoire dans les conteneurs et comparer les métriques avant / après en recette

    Une migration de JDK ne se fait jamais en même temps qu'une montée de framework majeure : un seul facteur à la fois, sinon le diagnostic devient impossible.

    Le tableau de synthèse

    Java 8 Java 17 Java 21
    Style dominant fonctionnel (streams, lambdas) données immuables (record, sealed) concurrence simple (threads virtuels)
    Syntaxe lambdas, streams, Optional record, sealed, text blocks, switch expression pattern matching complet, record patterns
    Concurrence ExecutorService, CompletableFuture idem threads virtuels, structured concurrency
    GC par défaut Parallel G1, ZGC disponible G1 / ZGC générationnel
    Conteneurs mal détectés (heap surdimensionné) limites cgroup respectées idem, démarrage plus rapide
    Spring Boot 2.x 3.x minimum 3.2+ recommandé
    Diagnostic jstack, jmap + JFR, helpful NPE idem, threads virtuels visibles en JFR

    Questions typiques, réponses courtes

    « Pourquoi migrer de 8 à 17 ou 21 ? » Trois raisons, dans cet ordre : le support (une version non maintenue est un risque de sécurité), les dépendances (Spring Boot 3 impose Java 17, et l'écosystème suit), et enfin les gains - performance GC, démarrage, threads virtuels, et un code plus court à maintenir. La syntaxe est le dernier argument, pas le premier.

    « Qu'apporte Java 21 concrètement ? » Les threads virtuels, qui permettent de tenir une forte concurrence d'entrées/sorties sans passer au réactif. Et le pattern matching, qui remplace les cascades de instanceof et de cast. Le premier point est architectural, le second est de la lisibilité.

    « record peut-il remplacer une entité JPA ? » Non : JPA exige un constructeur sans argument et des champs mutables. Le record sert aux DTO, aux projections et aux objets du domaine ; l'entité JPA reste dans l'adapter de persistance.

    « Qu'est-ce qui casse concrètement lors d'une migration ? » Les javax.* supprimés du JDK, l'encapsulation forte qui bloque la réflexion de vieilles librairies, les outils de bytecode à monter avant le JDK, et le dimensionnement mémoire en conteneur à revoir.
