    Java • Exceptions (hiérarchie, checked vs unchecked)

    Une exception n'est pas un accident : c'est un canal de communication entre le code qui détecte un problème et celui qui sait quoi en faire.

    Principe

    Une exception interrompt le flux normal et remonte la pile d'appels jusqu'à trouver un catch compatible. Si personne ne la traite, le thread s'arrête.

    1. La hiérarchie

    Throwable
├── Error                 ❌ ne jamais catcher • OutOfMemoryError, StackOverflowError
└── Exception
    ├── IOException       ✔️ checked • le compilateur impose de la gérer
    ├── SQLException      ✔️ checked
    └── RuntimeException  ✔️ unchecked • aucune obligation du compilateur
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IllegalStateException
        └── ArithmeticException
    Niveau Signification Réaction attendue
    Error la JVM est en difficulté ne pas catcher • laisser mourir le process
    Exception (checked) problème prévisible et récupérable traiter ou déclarer
    RuntimeException erreur de programmation ou panne technique remonter, logger, alerter

    2. Checked vs unchecked

    // Checked : le compilateur exige un traitement
public void lire(String chemin) throws IOException {
    Files.readAllLines(Path.of(chemin));
}

// Unchecked : rien n'est imposé
public void diviser(int a, int b) {
    int r = a / b; // ArithmeticException si b == 0
}
    Checked Unchecked
    Hérite de Exception RuntimeException
    Compilateur impose try/catch ou throws n'impose rien
    Sémantique cas prévu par la conception bug ou panne d'infrastructure
    Exemple métier règle de gestion violée que l'appelant doit traiter ressource introuvable, argument invalide

    Le choix est architectural

    Dans kore-batch, FunctionalException étend Exception délibérément : le compilateur force le processor à la catcher et à la comptabiliser dans la synthèse. Côté REST dans kore-hexagonal, les exceptions métier étendent RuntimeException : elles doivent remonter librement jusqu'au @RestControllerAdvice.

    Même besoin, deux contextes, deux choix opposés • le type d'exception se décide selon la stratégie de traitement, pas par habitude.

    3. try / catch / finally

    try {
    traiter(fichier);
} catch (FileNotFoundException e) {   // du plus spécifique...
    log.warn("Fichier absent : {}", fichier, e);
} catch (IOException e) {             // ...au plus général
    log.error("Erreur de lecture", e);
} finally {
    // exécuté dans tous les cas : succès, exception, return
    compteur.increment();
}

    Règles :

    • l'ordre des catch va du plus spécifique au plus général • l'inverse ne compile pas
    • finally s'exécute toujours, y compris après un return dans le try
    • un return dans le finally écrase l'exception en cours • à ne jamais faire

    Multi-catch

    catch (IOException | SQLException e) {
    log.error("Erreur d'accès aux données", e);
}

    4. try-with-resources

    Toute ressource qui implémente AutoCloseable est fermée automatiquement, même en cas d'exception.

    // Approche à éviter
BufferedReader reader = null;
try {
    reader = new BufferedReader(new FileReader(fichier));
    return reader.readLine();
} finally {
    if (reader != null) reader.close(); // verbeux, oubli fréquent
}

// try-with-resources
try (BufferedReader reader = new BufferedReader(new FileReader(fichier))) {
    return reader.readLine();
} // close() appelé automatiquement, même si readLine() lève une exception

    Plusieurs ressources sont fermées dans l'ordre inverse de leur ouverture.

    5. Exceptions personnalisées

    public class FunctionalException extends Exception {

    private final String component;
    private final String action;

    public FunctionalException(String component, String action, String message) {
        super(message);
        this.component = component;
        this.action = action;
    }
}

    Bonnes pratiques :

    • un nom qui décrit le problème métier • BookingNotFoundException, pas MyException
    • porter le contexte utile (référence, identifiant) en champs, pas seulement dans le message
    • une hiérarchie peu profonde • une exception racine par domaine suffit

    6. Conserver la cause

    // A eviter : la cause originale est perdue
catch (SQLException e) {
    throw new TechnicalException("Echec d'insertion"); // ❌ stack trace amputée
}

// Correct : chaînage
catch (SQLException e) {
    throw new TechnicalException("Echec d'insertion", e); // ✔️ "Caused by:" conservé
}

    Perdre la cause, c'est perdre la seule information qui permet le diagnostic en production.

    7. Anti-patterns

    catch (Exception e) { }                  // ❌ exception avalée en silence
catch (Throwable t) { }                  // ❌ attrape aussi les Error
catch (Exception e) { e.printStackTrace(); }  // ❌ invisible en production
    Anti-pattern Conséquence
    catch vide le bug existe mais devient invisible
    catch (Throwable) intercepte OutOfMemoryError • état de la JVM imprévisible
    printStackTrace() sort hors du système de logs, non collecté
    log et rethrow la même erreur apparaît 4 fois dans les logs
    exception pour du contrôle de flux coûteux et illisible • un if suffit
    throws Exception sur une signature l'appelant ne sait plus quoi traiter

    Points d'attention

    • catcher une exception qu'on ne sait pas traiter • mieux vaut laisser remonter
    • logger à chaque couche → bruit dans les logs et investigation ralentie
    • exposer une stack trace au client d'une API • fuite d'information
    • utiliser RuntimeException brute au lieu d'un type métier explicite
    • confondre Error et Exception

    Questions classiques

    Différence entre checked et unchecked ?

    Checked hérite de Exception et le compilateur impose de la gérer • unchecked hérite de RuntimeException et n'impose rien.

    Faut-il catcher Error ?

    Non • OutOfMemoryError ou StackOverflowError signifient que la JVM est en difficulté, le process doit s'arrêter.

    finally s'exécute-t-il après un return ?

    Oui, toujours • sauf arrêt brutal de la JVM (System.exit).

    À quoi sert try-with-resources ?

    À fermer automatiquement toute ressource AutoCloseable, y compris si une exception survient.

    Où logger une exception ?

    Une seule fois, à l'endroit où elle est réellement traitée • pas à chaque couche traversée.

    Une NPE en production, ça veut dire quoi ?

    Un bug, pas un cas métier • elle ne doit jamais atteindre le client.

    Synthèse

    • Throwable → Error (ne pas catcher) et Exception (checked / unchecked)
    • checked = cas prévu que l'appelant doit traiter • unchecked = bug ou panne technique
    • try-with-resources pour tout ce qui se ferme
    • toujours chaîner la cause lors d'une conversion d'exception
    • ne jamais avaler une exception, ne jamais la logger deux fois
