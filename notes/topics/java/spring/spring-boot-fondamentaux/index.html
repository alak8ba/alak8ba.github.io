    Spring Boot • Fondamentaux et avantages

    Spring Boot n'est pas un framework différent de Spring : c'est une surcouche qui supprime la configuration répétitive et rend une application Spring exécutable en autonomie.

    Principe

    Spring Boot répond à une seule question :

    comment démarrer une application Spring de production sans écrire 300 lignes de configuration ?

    Réponse : convention plutôt que configuration.

    Spring vs Spring Boot

    Spring (classique) Spring Boot
    Configuration XML ou @Configuration manuelle auto-configurée
    Dépendances choisies et alignées à la main starters cohérents
    Serveur WAR déployé sur Tomcat externe Tomcat embarqué, JAR exécutable
    Démarrage web.xml, DispatcherServlet déclarés une classe main()
    Production outillage à ajouter Actuator inclus

    Spring Boot ne remplace pas Spring • il l'assemble.

    Ce que Spring Boot apporte

    1. Auto-configuration

    Boot configure les beans en fonction de ce qu'il trouve dans le classpath.

    spring-boot-starter-data-jpa + un driver PostgreSQL + une URL JDBC → DataSource, EntityManagerFactory et TransactionManager sont créés automatiquement.

    2. Starters

    Un starter = un ensemble de dépendances cohérentes et testées ensemble.

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

    Cette seule ligne apporte Spring MVC, Jackson, la validation et Tomcat embarqué, dans des versions compatibles entre elles. Le spring-boot-starter-parent centralise les versions • on ne les écrit plus dans le POM.

    3. Serveur embarqué

    L'application est un JAR exécutable qui contient son serveur :

    java -jar application.jar

    Conséquence directe : le même artefact tourne sur le poste du développeur, en CI et en production • c'est ce qui rend la conteneurisation Docker naturelle.

    4. Configuration externalisée

    spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/app}
    username: ${DB_USER}
  jpa:
    hibernate:
      ddl-auto: validate

    Un seul binaire, N environnements • la configuration vient des variables d'environnement ou des profils, jamais du code.

    5. Production-ready (Actuator)

    /actuator/health     → état de l'application et de ses dépendances
/actuator/metrics    → métriques exposables vers Prometheus
/actuator/info       → version, commit, build

    Health checks et métriques sont disponibles sans écrire une ligne.

    Déclarer une application Spring Boot

    La classe de démarrage minimale :

    @SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

    Ce que @SpringBootApplication contient

    C'est une méta-annotation qui en regroupe trois :

    @Configuration        // la classe peut déclarer des @Bean
@EnableAutoConfiguration  // active l'auto-configuration
@ComponentScan        // scanne le package courant et ses sous-packages

    Point clé souvent demandé

    Le @ComponentScan part du package de la classe annotée. Un @Service placé dans un package frère (hors de l'arborescence) ne sera jamais détecté. D'où la règle : la classe Application se place à la racine du package applicatif.

    Comment fonctionne l'auto-configuration

    1. @EnableAutoConfiguration charge la liste des classes d'auto-configuration déclarées dans le fichier META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports de chaque JAR
    2. Chaque classe est conditionnée par des annotations @Conditional
    3. Seules les conditions satisfaites produisent des beans
    @AutoConfiguration
@ConditionalOnClass(DataSource.class)        // la classe est-elle au classpath ?
@ConditionalOnMissingBean(DataSource.class)  // l'ai-je déjà déclarée moi-même ?
public class DataSourceAutoConfiguration {
    // ...
}

    Le @ConditionalOnMissingBean est le mécanisme central : dès que tu déclares ton propre bean, Boot s'efface. L'auto-configuration ne t'enferme jamais.

    Pour voir ce qui a été auto-configuré et pourquoi :

    java -jar application.jar --debug

    Le rapport affiche les conditions matched et did not match.

    Ordre de précédence de la configuration

    Du plus fort au plus faible :

    Priorité Source
    1 arguments de ligne de commande (--server.port=8081)
    2 variables d'environnement (SERVER_PORT)
    3 application-{profil}.yml
    4 application.yml
    5 valeurs par défaut de l'auto-configuration

    Les profils activent des jeux de configuration :

    java -jar app.jar --spring.profiles.active=prod

    Impact réel aujourd'hui

    Spring Boot 3 impose Java 17 au minimum et s'aligne sur Jakarta EE • le passage depuis Boot 2 implique la migration javax.* → jakarta.*.

    Trois évolutions changent la donne côté exploitation :

    • Java 21 • les threads virtuels s'activent par configuration (spring.threads.virtual.enabled: true), sans réécrire le code métier
    • Conteneurisation • mvn spring-boot:build-image produit une image OCI sans Dockerfile, avec des couches séparées pour accélérer les rebuilds
    • Observabilité unifiée • Micrometer Observation remplace Sleuth : métriques et traces distribuées sont produites par la même instrumentation

    Le JAR autonome reste la raison pour laquelle Boot s'est imposé dans les architectures conteneurisées : un artefact, une commande, aucun serveur d'applications à administrer.

    Points d'attention

    • croire que Boot remplace Spring • c'est le même conteneur IoC en dessous
    • placer la classe Application ailleurs qu'à la racine du package → beans introuvables
    • laisser ddl-auto: update en production • schéma modifié à l'insu de l'équipe
    • exposer tous les endpoints Actuator sans authentification
    • ajouter un starter « au cas où » • chaque starter déclenche de l'auto-configuration

    Questions classiques

    Quels sont les avantages de Spring Boot ?

    Auto-configuration, starters, serveur embarqué, configuration externalisée, Actuator prêt pour la production.

    Que contient @SpringBootApplication ?

    @Configuration + @EnableAutoConfiguration + @ComponentScan.

    Comment démarre une application Boot ?

    Une classe main() qui appelle SpringApplication.run(...) • le JAR est exécutable, le serveur est embarqué.

    Comment fonctionne l'auto-configuration ?

    Des classes conditionnées par @ConditionalOnClass / @ConditionalOnMissingBean, listées dans AutoConfiguration.imports et chargées au démarrage.

    Comment désactiver une auto-configuration ?

    @SpringBootApplication(exclude = DataSourceAutoConfiguration.class), ou simplement déclarer soi-même le bean concerné.

    Boot est-il adapté aux microservices ?

    Oui • un JAR autonome par service, configuration externalisée, health checks et métriques natifs.

    Synthèse

    • Spring Boot = Spring + auto-configuration + starters + serveur embarqué
    • @SpringBootApplication = configuration + auto-configuration + scan de composants
    • l'auto-configuration est conditionnelle et s'efface devant tes propres beans
    • un seul artefact, la configuration vient de l'extérieur
    • Actuator rend l'application observable dès le premier jour
