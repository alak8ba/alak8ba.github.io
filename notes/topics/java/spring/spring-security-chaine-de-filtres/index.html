    Spring Security • la chaîne de filtres

    Contexte

    Spring Security paraît magique : on ajoute une dépendance, et toutes les URL deviennent protégées. Cette magie se paie plus tard, le jour où une règle ne s'applique pas et où personne ne sait pourquoi.

    Il n'y a pourtant qu'un seul mécanisme à comprendre : une chaîne de filtres servlet, placée avant le DispatcherServlet. Tout le reste en découle.

    flowchart LR
    R[Requete HTTP] --> F1[SecurityContextPersistenceFilter]
    F1 --> F2[Filtres d authentification<br/>JWT, form login, Basic]
    F2 --> F3[ExceptionTranslationFilter]
    F3 --> F4[AuthorizationFilter]
    F4 --> DS[DispatcherServlet]
    DS --> C[Controller]

    Le principe en une phrase

    La requête est authentifiée puis autorisée avant même d'atteindre le contrôleur. Si la chaîne rejette, aucun code métier n'est exécuté - et c'est exactement ce qu'on attend d'une sécurité : qu'elle s'applique en amont, pas dans chaque méthode.

    Authentification et autorisation

    Les deux mots sont employés l'un pour l'autre, alors qu'ils désignent deux étapes distinctes, dans cet ordre :

    Authentification Autorisation
    Question qui êtes-vous ? avez-vous le droit ?
    Échec 401 Unauthorized 403 Forbidden
    Produit un Authentication dans le SecurityContext une décision oui / non
    Porté par un filtre d'authentification AuthorizationFilter, @PreAuthorize

    401 ou 403 : la distinction qui est testée

    401 = « je ne sais pas qui tu es » : jeton absent, expiré, signature invalide. 403 = « je sais qui tu es, et tu n'as pas le droit ».

    Renvoyer 403 pour un jeton expiré envoie le client sur une mauvaise piste : il ne renouvellera pas son jeton, il croira à un problème de droits.

    La configuration moderne

    @Configuration
@EnableWebSecurity
@EnableMethodSecurity                       // active @PreAuthorize
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .securityMatcher("/api/**")                       // cette chaine ne vaut que pour /api
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/factures/**").hasAuthority("SCOPE_facture:read")
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())                // le filet de securite
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .csrf(csrf -> csrf.disable())                     // legitime SI aucun cookie d'auth
            .exceptionHandling(e -> e
                .authenticationEntryPoint(this::unauthorized)  // 401
                .accessDeniedHandler(this::forbidden))         // 403
            .build();
    }
}

    Quatre règles de lecture qui évitent la majorité des incidents :

    1. l'ordre compte : la première règle qui correspond gagne. Une règle large placée avant une règle précise rend la seconde inatteignable
    2. anyRequest().authenticated() en dernier : le filet. Sans lui, toute URL non listée est ouverte
    3. plusieurs SecurityFilterChain sont possibles, départagées par securityMatcher et ordonnées par @Order - une chaîne pour l'API stateless, une autre pour une IHM en session
    4. permitAll() n'est pas « pas de filtre » : la chaîne s'exécute quand même. Pour exclure vraiment (ressources statiques), c'est WebSecurityCustomizer.ignoring()

    Session ou jeton • le choix structurant

    Session serveur Jeton (JWT)
    Où est l'état côté serveur (mémoire ou Redis) dans le jeton, côté client
    Plusieurs instances session partagée obligatoire rien à partager
    Révocation immédiate : on détruit la session impossible avant expiration
    CSRF à protéger (le cookie part tout seul) sans objet si l'en-tête est explicite
    Adapté à IHM serveur classique API, SPA, mobile, microservices

    Le lien avec la production à N instances : une session en mémoire locale casse dès la deuxième instance - l'utilisateur est déconnecté une requête sur deux. → Le chemin d'une requête en production

    // Filtre JWT maison : le schema a connaitre, meme si oauth2ResourceServer fait mieux
public class JwtAuthFilter extends OncePerRequestFilter {   // OncePerRequest : une seule fois

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header != null && header.startsWith("Bearer ")) {
            try {
                Claims claims = verifier(header.substring(7));   // signature, iss, aud, exp
                var auth = new UsernamePasswordAuthenticationToken(
                        claims.getSubject(), null, autorites(claims));
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException e) {
                SecurityContextHolder.clearContext();            // on NE lance PAS d'exception ici
            }
        }
        chain.doFilter(req, res);   // le refus sera prononce par l'AuthorizationFilter
    }
}

    En production, préférer oauth2ResourceServer

    Un filtre maison oublie presque toujours quelque chose : la validation de l'audience, la rotation des clés via JWKS, la tolérance d'horloge, la gestion des algorithmes autorisés. Le support natif fait tout cela et se configure en trois lignes. → SSO • OAuth2, OIDC et SAML

    Rôles, autorités, scopes

    @PreAuthorize("hasRole('COMPTABLE')")                         // cherche ROLE_COMPTABLE
public void cloturer(FactureId id) { }

@PreAuthorize("hasAuthority('SCOPE_facture:write')")          // scope OAuth2 : prefixe SCOPE_
public void modifier(FactureId id) { }

// Autorisation qui depend de la DONNEE : elle ne peut pas etre dans la config
@PreAuthorize("@factureSecurity.appartientAuClient(#id, authentication.name)")
public Facture lire(FactureId id) { }

    Le préfixe ROLE_, source d'incidents silencieux

    hasRole("ADMIN") teste en réalité l'autorité ROLE_ADMIN. hasAuthority("ADMIN") teste ADMIN, sans préfixe. Un jeton qui porte ADMIN avec une règle hasRole("ADMIN") donne un 403 que personne ne comprend - la configuration a pourtant l'air juste.

    Deux niveaux complémentaires :

    • par URL, dans la configuration : grossier, lisible d'un coup d'œil
    • par méthode, avec @PreAuthorize : fin, et surtout le seul endroit où l'on peut décider en fonction de la donnée (« cet utilisateur peut-il voir cette facture ? »)

    CSRF et CORS • deux sujets différents

    CSRF CORS
    Protège de une action déclenchée à l'insu de l'utilisateur la lecture d'une réponse par un autre domaine
    Concerne les cookies, envoyés automatiquement le navigateur, pas le serveur
    Désactiver CSRF est légitime si l'authentification passe par un en-tête Authorization jamais : CORS se configure, il ne se « désactive » pas

    Le raccourci csrf.disable() ne vaut que pour une API sans cookie d'authentification. Avec une session en cookie, le désactiver ouvre une vraie faille. → CORS · Cookie Security

    Déboguer • le seul réflexe qui compte

    logging:
  level:
    org.springframework.security: DEBUG     # la chaine de filtres se raconte

    Au démarrage, Spring Security affiche la liste ordonnée des filtres. En DEBUG, chaque requête indique quel filtre a agi et pourquoi elle a été refusée. Quatre-vingt-dix pour cent des « pourquoi ça ne marche pas » se règlent là, en une minute.

    Symptôme Cause la plus fréquente
    Tout est ouvert pas de anyRequest(), ou chaîne non appliquée (securityMatcher)
    403 avec un jeton valide préfixe ROLE_ absent, ou autorités non mappées
    401 intermittent en cluster horloges désynchronisées, ou clé de signature différente
    403 sur POST seulement CSRF actif sans jeton anti-CSRF
    @PreAuthorize ignoré @EnableMethodSecurity oublié, ou appel interne à la classe (auto-invocation)
    Une route protégée devenue publique ordre des règles, ou chemin qui ne correspond plus

    Le risque des règles qui ne correspondent plus

    Une règle requestMatchers qui ne correspond à rien n'échoue pas : l'URL retombe simplement sur la règle suivante. Une route censée être protégée peut devenir publique sans la moindre erreur au démarrage.

    C'est arrivé en masse lors des migrations Spring Boot 2 → 3 (antMatchers → requestMatchers, fin de la tolérance du trailing slash). D'où la nécessité de tests d'accès : pour chaque route sensible, un test qui attend un 401 sans jeton et un 403 avec un rôle insuffisant. → Spring Boot 2 → 3

    Questions typiques, réponses courtes

    « Comment fonctionne Spring Security ? » C'est une chaîne de filtres servlet insérée avant le DispatcherServlet. Un filtre d'authentification établit l'identité et la place dans le SecurityContext ; un filtre d'autorisation décide ensuite si l'accès est permis. Le contrôleur n'est atteint que si les deux étapes passent.

    « Session ou JWT ? » Session pour une IHM serveur classique, avec l'avantage de la révocation immédiate. Jeton pour une API, une SPA ou du mobile : rien à partager entre instances, mais pas de révocation avant expiration - d'où des durées de vie courtes et un jeton de rafraîchissement révocable.

    « Différence entre hasRole et hasAuthority ? » hasRole("ADMIN") teste l'autorité ROLE_ADMIN : le préfixe est ajouté automatiquement. hasAuthority teste la chaîne exacte. C'est la cause la plus fréquente de 403 incompréhensibles.

    « Où placer l'autorisation : URL ou méthode ? » Les deux. Par URL pour le grossier, lisible en un coup d'œil. Par méthode avec @PreAuthorize pour le fin - et c'est le seul endroit où une décision peut dépendre de la donnée elle-même.

    « Peut-on désactiver CSRF ? » Seulement si l'authentification ne repose sur aucun cookie envoyé automatiquement par le navigateur - typiquement une API en Authorization: Bearer. Avec une session en cookie, le désactiver ouvre une faille réelle.
