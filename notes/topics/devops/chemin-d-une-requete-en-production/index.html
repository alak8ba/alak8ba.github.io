    Le chemin d'une requête en production • du DNS à l'instance

    Contexte

    « Vous avez plusieurs serveurs en production : comment le trafic arrive-t-il jusqu'à une instance ? »

    Question redoutable parce qu'elle ne se répond pas avec un nom d'outil. Elle demande de dérouler une chaîne - et chaque maillon de cette chaîne est un endroit où ça casse.

    La chaîne complète

    flowchart TD
    U[Navigateur] -->|1. resolution DNS| DNS[DNS]
    U -->|2. TLS + HTTP| LB[Load balancer / entree publique]
    LB -->|3. terminaison TLS, X-Forwarded-For| RP[Reverse proxy - nginx]
    RP -->|4. routage par domaine et chemin| GW[API Gateway]
    GW -->|5. jeton, quotas, correlation| SVC[Service : N instances]
    SVC --> DB[(Base)]
    SVC --> K[(Kafka)]
    Étage Rôle Ce qui s'y décide
    DNS nom → adresse TTL, bascule de site, répartition géographique
    Load balancer répartir entre les entrées santé des nœuds, algorithme, persistance
    Reverse proxy (nginx) exposer, terminer TLS, servir le statique certificats, en-têtes, timeouts, compression
    API Gateway sécurité et contrats d'API validation de jeton, quotas, routage par version
    Instances le service lui-même sans état, N réplicas, arrêt gracieux

    Trois composants qu'on confond

    • Load balancer : répartit la charge (souvent L4, parfois L7)
    • Reverse proxy : expose, termine TLS, route par domaine et chemin
    • API Gateway : ajoute la couche API - jetons, quotas, versions, observabilité

    Un même outil peut jouer plusieurs rôles (nginx fait proxy et répartition ; Traefik aussi). Ce qui compte, c'est de savoir quelle fonction est assurée où. → API Gateway · Reverse Proxy Pattern

    Étage 1 • le DNS

    api.exemple.fr.   60   IN   A   203.0.113.10

    Le TTL décide de la vitesse de bascule : un TTL de 3600 s signifie qu'après un changement, des clients continueront d'aller à l'ancienne adresse pendant une heure. D'où la règle : TTL court (30 à 60 s) sur les enregistrements susceptibles de basculer.

    Le DNS répartit grossièrement (round-robin, géo), mais il ne sait pas qu'un serveur est tombé. Ce n'est pas un mécanisme de haute disponibilité : c'est le load balancer qui porte cette responsabilité.

    Étage 2 et 3 • nginx en frontal

    upstream facturation {
    least_conn;                               # vers l'instance la moins chargee
    server 10.0.1.11:8080 max_fails=3 fail_timeout=15s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=15s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=15s;
    keepalive 32;                             # connexions reutilisees vers l'amont
}

server {
    listen 443 ssl http2;
    server_name api.exemple.fr;

    ssl_certificate     /etc/letsencrypt/live/api.exemple.fr/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.exemple.fr/privkey.pem;

    location /api/ {
        proxy_pass http://facturation;

        # L'application doit savoir QUI appelle vraiment, et en quel protocole
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 3s;
        proxy_send_timeout   30s;
        proxy_read_timeout   30s;            # doit etre < timeout applicatif
    }
}

    Les algorithmes de répartition :

    Algorithme Principe Quand
    round_robin à tour de rôle requêtes homogènes (défaut)
    least_conn vers la moins occupée durées de traitement variables
    ip_hash la même IP va toujours au même nœud contournement d'un état de session mal placé

    Les deux pièges de l'étage frontal

    X-Forwarded-For oublié : l'application voit l'IP du proxy pour tous les clients. Conséquences directes : logs inexploitables, limitation de débit par IP inopérante, et géolocalisation fausse. Côté Spring, il faut aussi traiter l'en-tête (server.forward-headers-strategy=framework), sinon les URL générées sont en http alors que le client est en https.

    Timeouts non alignés : si nginx coupe à 30 s et que l'application travaille jusqu'à 60 s, le client reçoit une 504 pendant que le traitement continue côté serveur - et peut être relancé, donc exécuté deux fois. La règle : timeout client > timeout proxy > timeout applicatif, jamais l'inverse.

    Étage 5 • plusieurs instances, donc pas d'état

    C'est le point central de la question. Trois instances derrière un répartiteur, cela impose des contraintes que le développement local ne montre jamais.

    Ce qui casse avec N instances Pourquoi La réponse
    Session HTTP en mémoire la requête suivante tombe sur une autre instance jeton stateless, ou session dans Redis
    Cache local trois caches divergents cache distribué, ou TTL court assumé
    Tâche planifiée @Scheduled exécutée trois fois verrou distribué (ShedLock), ou instance dédiée
    Fichier écrit sur disque local invisible des autres instances stockage objet partagé
    Compteur ou séquence en mémoire valeurs divergentes séquence en base, ou Redis
    WebSocket / SSE le client est attaché à une instance persistance de session ou bus de diffusion

    La formulation qui résume

    « Une instance ne doit rien détenir qu'une autre ne puisse retrouver. Tout état partagé sort du processus : base, cache distribué, broker. C'est ce qui rend une instance jetable - et c'est ce qui rend possibles la montée en charge, le déploiement progressif et l'auto-réparation. »

    ip_hash ou les sticky sessions sont un contournement : ils font tenir un état mal placé, au prix d'une répartition déséquilibrée et de sessions perdues à chaque redémarrage.

    Santé, bascule et déploiement

    # nginx retire une instance apres 3 echecs, pendant 15 s
server 10.0.1.11:8080 max_fails=3 fail_timeout=15s;

    Deux notions de santé à ne pas confondre - c'est exactement la distinction readiness / liveness de Kubernetes :

    • prête à recevoir du trafic : dépendances disponibles, cache chargé
    • vivante : le processus fonctionne encore

    Pour un déploiement sans coupure, il faut toute la séquence :

    1. la nouvelle instance démarre et déclare prête seulement quand elle l'est
    2. le répartiteur commence à l'utiliser
    3. l'ancienne est retirée de la rotation avant d'être arrêtée
    4. elle termine ses requêtes en cours - arrêt gracieux
    server:
  shutdown: graceful                 # Spring Boot : on finit les requetes en cours
spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s

    Sans arrêt gracieux, chaque déploiement coupe les requêtes en vol : des 502 visibles par les utilisateurs, à chaque livraison. → Kubernetes • fondamentaux · Docker Compose vs Kubernetes

    Quand ça va mal • par où on regarde

    Symptôme Étage probable Vérification
    502 Bad Gateway l'amont ne répond pas l'instance est-elle démarrée, le port correct ?
    504 Gateway Timeout traitement plus long que le timeout proxy aligner les timeouts, chercher la lenteur
    503 intermittent toutes les instances marquées en échec sonde de santé trop stricte ou trop rapide
    401 aléatoire une instance n'a pas la bonne configuration vérifier la config déployée sur chaque nœud
    Fonctionne une fois sur trois une instance est en mauvais état isoler par les logs, comparer les nœuds
    Utilisateur déconnecté au hasard session en mémoire locale passer en stateless ou session partagée
    Certificat expiré frontal renouvellement automatique et supervisé

    Le réflexe « une fois sur trois »

    Un comportement intermittent à fréquence régulière avec N instances désigne presque toujours une instance déviante : configuration différente, version antérieure, disque plein. Le premier geste est de sortir cette instance de la rotation - pas de relancer tout le service.

    Chaque requête doit porter un identifiant de corrélation, propagé du frontal jusqu'aux services, sinon un parcours reste introuvable dans les logs. → Distributed Tracing And Correlation

    Questions typiques, réponses courtes

    « Comment le trafic arrive-t-il jusqu'à l'application ? » DNS pour résoudre le nom, un point d'entrée public qui termine le TLS et répartit, un reverse proxy qui route par domaine et chemin en ajoutant X-Forwarded-For, éventuellement une gateway qui valide le jeton et applique les quotas, puis N instances sans état derrière. Chaque étage a ses timeouts et ses sondes de santé.

    « Différence entre load balancer, reverse proxy et API gateway ? » Le load balancer répartit ; le reverse proxy expose, termine TLS et route ; la gateway ajoute la couche API - jetons, quotas, versions, observabilité. Un même produit peut assurer plusieurs de ces rôles, mais ce sont trois fonctions distinctes.

    « Que faut-il changer quand on passe à plusieurs instances ? » Tout ce qui est en mémoire locale : session HTTP, cache, planification, fichiers, compteurs. La session part dans un jeton ou dans Redis, le cache devient distribué, les tâches planifiées sont protégées par un verrou distribué. Une instance ne doit rien détenir qu'une autre ne puisse retrouver.

    « Comment déploie-t-on sans coupure ? » Sonde de disponibilité fiable, retrait de la rotation avant l'arrêt, arrêt gracieux qui laisse finir les requêtes en cours, et une bascule progressive instance par instance. Plus une compatibilité ascendante du schéma de base, puisque deux versions cohabitent. → Migrations de schéma

    « Que signifie une 502 et une 504 ? » 502 : le proxy a joint l'amont mais la réponse est invalide ou la connexion refusée - typiquement l'instance est tombée. 504 : l'amont n'a pas répondu dans le délai imparti - le traitement est trop long, ou bloqué.
