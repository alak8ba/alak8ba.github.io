    API Gateway • rôle, limites et alternatives

    Contexte

    Dès qu'un système est découpé en plusieurs services, chacun doit traiter les mêmes préoccupations transverses :

    • terminaison TLS et exposition publique
    • authentification et validation des jetons
    • limitation de débit, quotas, protection contre les abus
    • journalisation, corrélation, métriques
    • versionnement et compatibilité des contrats

    Les dupliquer dans chaque service produit N implémentations divergentes : un correctif de sécurité doit être appliqué N fois, et le client doit connaître l'adresse de chaque service.

    L'API Gateway est le point d'entrée unique qui porte ces préoccupations une seule fois.

    flowchart LR
    C1[Front web] --> GW[API Gateway]
    C2[Mobile] --> GW
    C3[Partenaire] --> GW

    GW --> S1[Service Clients]
    GW --> S2[Service Facturation]
    GW --> S3[Service Stock]

    GW -.->|validation du jeton| IDP[Identity Provider]
    GW -.->|traces et metriques| OBS[Observabilite]

    Ce que porte une gateway

    Responsabilité Détail
    Routage une URL publique → un service interne, avec réécriture de chemin
    Terminaison TLS certificats centralisés, renouvellement au même endroit
    Authentification validation de signature, iss, aud, exp du jeton - rejet en 401 avant tout appel interne
    Autorisation grossière « ce scope a le droit d'appeler cette route »
    Rate limiting / quotas par client, par clé d'API, par IP
    Résilience timeouts, retries, circuit breaker, bulkhead
    Observabilité génération du correlation-id, logs d'accès, métriques par route
    Transformation en-têtes, versions de contrat, adaptation de format
    Agrégation légère un appel client → deux ou trois appels internes fusionnés
    Cache réponses publiques et coûteuses

    Ce qu'elle ne doit pas porter

    La dérive classique : la god gateway

    Une gateway qui accumule des règles métier devient un composant central que personne n'ose modifier - un monolithe déguisé en configuration, avec un déploiement commun à toutes les équipes.

    Restent hors de la gateway :

    • les règles métier (calcul de prix, validation fonctionnelle, workflow)
    • l'orchestration de plusieurs services pour un cas d'usage → un service dédié ou un BFF
    • l'autorisation fine dépendant des données (« cet utilisateur peut-il voir cette facture ? ») → seul le service propriétaire de la donnée peut décider
    • la persistance : une gateway reste sans état

    Gateway, reverse proxy, load balancer, service mesh, BFF

    Ces cinq termes sont souvent confondus. Ils opèrent à des niveaux différents.

    Composant Niveau Rôle Exemples
    Load balancer L4 / L7 répartir la charge entre instances HAProxy, ELB
    Reverse proxy L7 exposer, router, terminer TLS Nginx, Traefik, Apache
    API Gateway L7, orienté API proxy + sécurité, quotas, contrats, observabilité Spring Cloud Gateway, Kong, APISIX, Apigee, AWS API Gateway
    Service mesh infrastructure, trafic interne mTLS, retries, routage entre services (sidecar) Istio, Linkerd
    BFF applicatif une API taillée pour un client donné un service Spring Boot par frontal

    Les deux distinctions à garder claires :

    • gateway vs reverse proxy - tout API gateway est un reverse proxy ; l'inverse est faux. La gateway ajoute la couche API : jetons, quotas, versions, métriques par route. Un Nginx avec trois location n'est pas une gateway.
    • gateway vs service mesh - la gateway traite le trafic nord-sud (extérieur → système), le mesh le trafic est-ouest (service → service). Ils se complètent et ne se remplacent pas.
    flowchart TD
    EXT[Clients externes] -->|nord-sud| GW[API Gateway]
    GW --> A[Service A]
    A <-->|est-ouest, mTLS| B[Service B]
    A <-->|est-ouest| C[Service C]

    Le cas du BFF

    Un frontal web et une application mobile n'ont pas les mêmes besoins : la mobile veut peu de champs et peu d'appels, le web veut des vues riches. Faire porter ces différences par la gateway la remplit de logique de présentation.

    Le BFF (Backend For Frontend) est un service par frontal, appartenant à l'équipe qui développe ce frontal. Il agrège, met en forme, et - cas très courant - porte le flux OIDC et garde les jetons côté serveur. → SSO

    Exemple • Spring Cloud Gateway

    spring:
  cloud:
    gateway:
      routes:
        - id: facturation
          uri: lb://facturation-service
          predicates:
            - Path=/api/facturation/**
          filters:
            - StripPrefix=2
            - name: CircuitBreaker
              args:
                name: facturationCB
                fallbackUri: forward:/fallback/facturation
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 20
                redis-rate-limiter.burstCapacity: 40
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.exemple.fr/realms/interne

    Points d'attention sur cette implémentation :

    • Spring Cloud Gateway est réactif (WebFlux, Netty) : y écrire du code bloquant sature la boucle d'événements et fait tomber toute la gateway, pas un seul appel
    • le rate limiter a besoin d'un état partagé (Redis) dès qu'il y a plusieurs instances, sinon la limite est multipliée par le nombre d'instances
    • StripPrefix et la réécriture de chemin sont la première cause de 404 en recette

    Sécurité • qui valide quoi

    La gateway ne dispense pas les services de vérifier

    Si un service accepte tout ce qui vient de la gateway, alors n'importe quel appel interne - un autre service compromis, un pod dans le même namespace, un développeur en port-forward - devient une authentification valide.

    Le partage de responsabilité qui tient en production :

    Couche Ce qu'elle vérifie
    Gateway signature, iss, aud, exp, scope de la route, débit, taille, format
    Service revalide le jeton, applique l'autorisation métier sur la donnée
    Réseau mTLS ou politiques réseau : seul le trafic de la gateway atteint les services

    Trois façons de propager l'identité vers l'intérieur :

    1. transmettre le jeton tel quel - simple, le service revalide (le plus courant)
    2. token exchange - la gateway échange le jeton externe contre un jeton interne à durée très courte, audience restreinte
    3. en-têtes de confiance (X-User-Id) - à n'utiliser que si le réseau garantit qu'aucun autre appelant ne peut atteindre le service, sinon c'est une usurpation triviale

    Coûts et risques

    Risque Conséquence Atténuation
    Point de défaillance unique tout le SI est indisponible plusieurs instances, sans état, sur plusieurs zones
    Un saut réseau de plus latence ajoutée sur chaque appel garder la gateway légère, mesurer le temps passé dedans
    Goulot d'étranglement la gateway sature avant les services dimensionner, surveiller CPU et connexions
    Couplage organisationnel chaque équipe attend un déploiement de gateway configuration déclarative par équipe, GitOps
    Fuite de logique métier la gateway devient impossible à faire évoluer revue systématique de ce qui y entre
    Configuration non testée régression détectée en production tests de routes en CI, environnement de recette identique

    Faut-il une gateway ?

    Situation Réponse raisonnable
    Un seul service exposé non - un reverse proxy suffit
    Quelques services, un seul frontal interne reverse proxy + sécurité dans les services
    Plusieurs services et plusieurs types de clients oui
    API ouverte à des partenaires, quotas et facturation oui, avec gestion des clés d'API
    Beaucoup de trafic interne service à service gateway au bord + service mesh à l'intérieur

    Questions typiques, réponses courtes

    « Différence entre API Gateway et reverse proxy ? » Le reverse proxy route et expose. La gateway ajoute la couche API : validation de jetons, quotas, contrats, observabilité par route, résilience. Tout gateway est un reverse proxy, pas l'inverse.

    « Faut-il valider le jeton dans la gateway ou dans le service ? » Les deux. La gateway rejette tôt et protège les services d'un trafic non authentifié ; le service revalide parce qu'il ne peut pas supposer que tout appel interne est légitime.

    « Où placer l'agrégation d'appels ? » Une agrégation technique légère peut rester en gateway. Dès qu'elle est spécifique à un frontal ou porte de la logique, elle va dans un BFF.

    « Comment éviter que la gateway devienne un point de défaillance ? » Elle reste sans état - donc réplicable -, elle est déployée en plusieurs instances derrière un load balancer, elle porte des timeouts et un circuit breaker par route, et elle est surveillée par route et non globalement.
