    Panorama backend Java / Spring • Synthèse d'un échange technique

    Note de contexte (2 septembre 2026) : cette page consolide un échange technique avec un expert du domaine. Les thèmes parcourus sont repris ici dans l'ordre où ils s'enchaînent naturellement, du langage jusqu'à l'exploitation. Chaque section donne l'essentiel et renvoie vers la fiche détaillée.

    Principe

    Une page unique pour relire l'ensemble du socle backend Java/Spring : ce qui doit être disponible immédiatement, sans avoir à ouvrir quinze fiches.

    Le fil conducteur de tout ce qui suit tient en une phrase :

    découpler pour pouvoir changer une partie sans casser les autres

    Injection de dépendances et Strategy au niveau de la classe. Hexagonale et SOLID au niveau du module. Kafka et l'event-driven au niveau des services. Les tests vérifient que le découplage tient, le RUN constate ce qui se passe quand il ne tient pas.

    1. Java • le socle

    Langage orienté objet à typage statique fort, compilé en bytecode exécuté par la JVM — d'où la portabilité entre systèmes. Mémoire gérée par un garbage collector, ce qui supprime la libération manuelle mais déplace le sujet vers le tuning GC et l'analyse des fuites.

    Les versions structurantes aujourd'hui :

    Version Ce qu'elle apporte au quotidien
    Java 8 lambdas, Stream, Optional
    Java 11 LTS, var, HTTP Client
    Java 17 LTS, record, sealed, pattern matching
    Java 21 LTS, threads virtuels, pattern matching pour switch

    → Java en Production • Deep-Dive

    2. Exceptions

    Throwable est la racine de tout ce qui peut être lancé ou attrapé. Deux branches :

    Throwable
├── Error                 la JVM est en difficulté (OutOfMemoryError, StackOverflowError)
│                         → on ne les rattrape pas
└── Exception
    ├── checked           le compilateur impose de traiter ou déclarer (IOException)
    └── RuntimeException  unchecked, remonte librement (NullPointerException,
                          IllegalArgumentException, IllegalStateException)

    Le point à comprendre : checked ou unchecked est un choix de conception, pas une habitude.

    • une exception checked force l'appelant à décider quoi faire • pertinent quand l'erreur fait partie du fonctionnement normal et doit être comptabilisée
    • une exception unchecked traverse les couches sans les polluer • pertinent quand le traitement est centralisé plus haut

    Trois règles constantes : try-with-resources pour tout ce qui se ferme, toujours chaîner la cause (new TechnicalException(message, e)), et logger une seule fois, là où l'erreur est réellement traitée.

    → Java • Exceptions · Gestion des exceptions dans Spring Boot

    3. Concurrence et exclusion mutuelle

    L'exclusion mutuelle garantit qu'un seul thread accède à une ressource partagée à la fois. Trois problèmes distincts, à ne pas confondre :

    Problème Cause Réponse
    Race condition count++ n'est pas atomique : lire, incrémenter, écrire synchronized, AtomicInteger, Lock
    Visibilité un thread ne voit pas la modification faite par un autre volatile
    Deadlock verrous acquis dans un ordre incohérent ordre strict, tryLock avec timeout

    Le piège classique : volatile garantit la visibilité, pas l'atomicité. volatile int count; count++; reste non thread-safe.

    AtomicInteger repose sur le CAS (compare-and-set) : thread-safe sans verrou, donc plus performant sur les opérations simples. Au-delà, ExecutorService borne les ressources — on ne crée pas un thread par tâche, on soumet des tâches à un pool dimensionné selon la nature du travail (CPU-bound ou IO-bound).

    Le pont avec Spring : un bean singleton avec un état mutable est une race condition. C'est la raison pour laquelle un service reste stateless.

    → Race Condition · Deadlock · ExecutorService & CompletableFuture

    4. Héritage et composition

    L'héritage crée un couplage fort : l'enfant dépend de l'implémentation du parent, et toute évolution du parent se propage. La composition, elle, assemble des comportements sans figer la hiérarchie.

    La règle pratique : héritage quand la relation « est un » est évidente et stable, composition partout ailleurs. Le polymorphisme s'obtient très bien par interface, sans hériter d'une implémentation.

    Le lien avec SOLID : le principe de Liskov n'est respecté que si la sous-classe peut réellement remplacer le parent sans surprise. Une sous-classe qui redéfinit une méthode pour lever UnsupportedOperationException viole ce contrat.

    → Héritage · Polymorphisme · SOLID

    5. Clean code et bonnes pratiques

    Le nom porte l'intention. Fonctions courtes, un seul niveau d'abstraction, pas de paramètre booléen — il cache deux méthodes en une. Le commentaire explique le pourquoi, jamais le quoi. Optional plutôt que null, exception plutôt que code retour, jamais de catch vide.

    La formulation qui résume tout :

    La difficulté à écrire un test est un signal de conception, pas un problème de test.

    Une classe qu'on ne parvient pas à tester a trop de responsabilités (SRP) ou fabrique ses dépendances avec new (DIP). Clean code, SOLID et testabilité décrivent le même sujet sous trois angles.

    Le contrepoint qui évite le dogmatisme : DRY s'applique à la connaissance métier, pas aux lignes qui se ressemblent. Factoriser deux codes similaires par coïncidence crée un couplage artificiel qu'on paiera au premier changement.

    → Clean Code

    6. Architecture en couches • Repository et Service

    Une séparation simple et systématiquement demandée :

    Couche Responsabilité Ce qu'elle ne fait pas
    Controller adapter HTTP ↔ métier aucune règle métier
    Service logique métier, orchestration, transactions pas de SQL, pas de HTTP
    Repository accès aux données, abstraction de la base aucune règle métier

    Le service coordonne un ou plusieurs repositories et porte la frontière transactionnelle (@Transactional). Le repository ne parle qu'à la base.

    @Repository est d'ailleurs le seul stéréotype Spring à apporter un comportement réel : il traduit les exceptions techniques JDBC/JPA en DataAccessException, ce qui évite de faire remonter des exceptions propres au driver jusqu'au métier.

    → Hexagonal Architecture · Déclarer un bean Spring

    7. Architecture applicative • hexagonale, CQRS, event-driven

    Hexagonale : le domaine au centre, sans dépendance vers l'infrastructure. Des ports (interfaces définies par le domaine) et des adapters (REST, JPA, Kafka) qui les implémentent. Les dépendances pointent toujours vers l'intérieur. Bénéfice concret : le domaine se teste sans base et sans Spring, en millisecondes.

    CQRS • Command Query Responsibility Segregation : séparer le modèle d'écriture du modèle de lecture.

    • écriture : modèle normalisé, garant des invariants métier
    • lecture : modèle dénormalisé, optimisé pour la requête

    Ce que ça apporte : chaque modèle se simplifie et se dimensionne indépendamment. Ce que ça coûte : cohérence éventuelle entre les deux et complexité supplémentaire. Souvent associé à l'Event Sourcing, mais les deux sont indépendants — on peut faire l'un sans l'autre.

    Event-driven : les services communiquent par événements plutôt que par appels synchrones. Le découplage se paie par trois obligations : cohérence éventuelle assumée, consumers idempotents (la livraison at-least-once produit des doublons), et outbox pattern pour ne jamais publier un événement dont la transaction est ensuite annulée.

    → CQRS Pattern · Idempotent Consumers · Outbox Pattern

    8. Design patterns • et où ils vivent réellement

    Ce qui distingue une connaissance livresque d'une pratique : savoir où le pattern est déjà là, dans le framework qu'on utilise tous les jours.

    Pattern Problème résolu Où on le rencontre
    Strategy remplacer une chaîne de if/else sur un type, ajouter un cas sans modifier l'existant Comparator, SkipPolicy, PasswordEncoder
    Builder construire un objet complexe, immuable, validé dans build() ResponseEntity, StepBuilder, TopicBuilder
    Observer notifier N abonnés sans que l'émetteur les connaisse ApplicationEventPublisher + @EventListener
    Factory centraliser la création BeanFactory
    Singleton une instance partagée scope Spring par défaut
    DI / IoC la classe reçoit ses dépendances au lieu de les créer tout Spring

    Deux prolongements qui montrent la compréhension du mécanisme :

    Spring injecte toutes les implémentations d'une interface dans une List ou une Map<String, Interface> • c'est le mariage naturel entre Strategy et le conteneur, et on n'y écrit jamais de new.

    Observer et Kafka sont le même modèle à deux échelles : @EventListener découple des modules dans une JVM (synchrone par défaut, en mémoire, perdu au crash), Kafka découple des services (durable, rejouable, at-least-once). Et @TransactionalEventListener(AFTER_COMMIT) évite l'effet de bord irréversible — un email envoyé pour une transaction finalement annulée.

    → Strategy · Builder · Observer

    9. IoC et injection de dépendances

    L'inversion de contrôle : ce n'est plus le code applicatif qui crée ses collaborateurs et pilote le flux, c'est le conteneur qui instancie, câble, gère le cycle de vie et appelle le code. Le conteneur, dans Spring, c'est l'ApplicationContext.

    L'injection de dépendances est le mécanisme concret qui réalise ce principe. IoC est l'idée, DI en est la mise en œuvre.

    Deux façons de déclarer un bean, un seul critère de choix : est-ce que je possède la classe ?

    // Oui : annotation sur la classe
@Service
public class BookingService { }

// Non (classe d'une librairie) : méthode de fabrique dans une @Configuration
@Configuration
public class JacksonConfig {

    @Bean
    public ObjectMapper objectMapper() {
        return JsonMapper.builder().addModule(new JavaTimeModule()).build();
    }
}

    @Component, @Service et @Repository sont techniquement identiques — même mécanisme, même cycle de vie. La différence est sémantique, elle documente l'intention. Seul @Repository ajoute un comportement : la traduction d'exceptions.

    Injection par constructeur : champs final, dépendances visibles dans la signature, classe instanciable sans conteneur dans un test. @Autowired est inutile depuis Spring 4.3 quand il n'y a qu'un constructeur.

    Deux implémentations du même type provoquent une NoUniqueBeanDefinitionException au démarrage — ce qui est préférable à une surprise en production. Trois réponses : @Primary (défaut global), @Qualifier (choix au point d'injection), ou injecter la Map de toutes les implémentations.

    → Déclarer un bean Spring · Scope des beans · Injection de dépendances

    10. Spring et Spring Boot

    Spring Boot n'est pas un framework différent : c'est le même conteneur IoC, pré-assemblé.

    Spring Spring Boot
    Configuration XML ou @Configuration manuelle auto-configurée
    Dépendances alignées à la main starters cohérents
    Serveur WAR déployé sur un Tomcat externe Tomcat embarqué, JAR exécutable
    Démarrage web.xml, DispatcherServlet déclarés une classe main()
    Production outillage à ajouter Actuator inclus

    Les cinq apports : auto-configuration, starters, serveur embarqué, configuration externalisée, Actuator.

    Comment fonctionne l'auto-configuration : des classes listées dans AutoConfiguration.imports, conditionnées par @ConditionalOnClass (la classe est-elle au classpath ?) et @ConditionalOnMissingBean (l'ai-je déjà déclarée moi-même ?). Dès qu'un bean est déclaré explicitement, Boot s'efface — l'auto-configuration n'enferme jamais.

    Déclarer l'application :

    @SpringBootApplication   // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

    Le scan part du package de cette classe : elle se place à la racine du package applicatif, sinon des beans restent introuvables.

    → Spring Boot • Fondamentaux et avantages

    11. @Controller vs @RestController

    @RestController = @Controller + @ResponseBody

    @Controller retourne un nom de vue résolu par un ViewResolver (HTML). @RestController retourne les données, sérialisées en JSON par Jackson. Le piège classique : un @Controller qui retourne "ok" sans @ResponseBody fait chercher une vue nommée ok et échoue en 500.

    Trois réflexes qui vont avec :

    • ResponseEntity pour maîtriser le code HTTP • 201 avec en-tête Location sur une création, 204 sur une suppression
    • DTO en entrée et en sortie, jamais l'entité JPA • sinon le modèle de persistance fuit dans le contrat d'API
    • gestion des erreurs centralisée dans un @RestControllerAdvice, pas répétée dans chaque contrôleur

    → @Controller vs @RestController

    12. Spring Batch

    Le modèle : un Job est une suite de Steps. Un step chunk-oriented enchaîne ItemReader → ItemProcessor → ItemWriter et commite toutes les N lignes — c'est ce qui permet de traiter des millions d'enregistrements sans saturer la mémoire ni tenir une transaction géante.

    L'état : le JobRepository persiste l'exécution en base (BATCH_JOB_EXECUTION, BATCH_STEP_EXECUTION). Conséquence directe : un job interrompu redémarre là où il s'est arrêté, et une même instance de job ne se rejoue pas par accident.

    @StepScope fait deux choses : le late binding des paramètres du job (#{jobParameters['inputFile']}, connu seulement à l'exécution) et une instance neuve par exécution de step et par partition — donc un état isolé, sans fuite entre partitions parallèles.

    La volumétrie : le partitionnement découpe un step en partitions traitées en parallèle, chacune avec son reader et son processor.

    Le traitement des erreurs : plutôt que le mécanisme de skip natif, catcher l'exception fonctionnelle dans le processor • pas de throw, donc pas de rollback transactionnel, chaque item en erreur est comptabilisé avec sa référence, et le rapport final liste précisément les causes.

    → Spring Batch • Patterns avancés · Migration SB4/Java 8 → SB5/Java 21

    13. Tests • la démarche

    La pyramide d'abord : beaucoup d'unitaires (domaine pur, sans contexte Spring), quelques tests d'intégration, peu d'E2E.

    La démarche, étape par étape

    1. Identifier quoi tester • la logique métier, les cas limites, les branches conditionnelles. Pas les getters, pas le framework, pas le code sans logique.

    2. Rendre le code testable • injection par constructeur, pas de new sur les dépendances, pas de LocalDateTime.now() en dur — on injecte une Clock.

    3. Structurer en Arrange / Act / Assert

    @Test
void doit_appliquer_la_remise_fidelite_au_dela_de_100_euros() {
    // Arrange
    var client = new Client(Statut.FIDELE);
    var panier = new Panier(client, 120.0);

    // Act
    var total = panier.calculerTotal();

    // Assert
    assertThat(total).isEqualTo(108.0);
}

    Le nom décrit le comportement attendu, pas la méthode appelée.

    4. Couvrir les cas limites • nominal, frontières (99.99 / 100 / 100.01), null, collection vide, exception attendue. @ParameterizedTest évite la répétition.

    5. Ne mocker que ce qui sort de l'unité • repository, client HTTP, envoi de mail. Jamais un objet de valeur ni une classe du domaine : on l'instancie.

    6. Vérifier que le test échoue d'abord • un test qui passe du premier coup peut ne rien tester. Casser volontairement la logique valide que le test réagit.

    7. Automatiser • exécution en CI sur chaque PR, build rouge si un test échoue.

    Les tranches Spring

    On ne met pas @SpringBootTest partout. @WebMvcTest ne charge que la couche web et teste un contrôleur avec MockMvc — vraies requêtes à travers le DispatcherServlet, sans serveur. @DataJpaTest ne charge que la couche persistance, chaque test étant transactionnel et rollbacké. La suite passe de plusieurs minutes à quelques secondes.

    Testcontainers plutôt que H2 pour l'intégration : une vraie base jetable, au comportement identique à la production.

    Enfin, la couverture mesure les lignes exécutées, pas la pertinence des assertions. Ce qui compte : chaque invariant métier testé, chaque endpoint avec son cas d'erreur, chaque consumer testé avec un doublon d'événement.

    Le réflexe qui vaut pour tout bug de production : écrire d'abord le test qui le reproduit. Il échoue, on corrige, il passe — et il devient une garantie de non-régression.

    → JUnit 5, Mockito & Spring Boot Test · Testcontainers

    14. Sécurité applicative • les risques OWASP

    L'OWASP publie une liste de référence des risques applicatifs web, mise à jour périodiquement. Les catégories qui reviennent le plus, et leur traduction concrète côté Spring :

    Risque Traduction concrète
    Broken Access Control un utilisateur accède à une ressource qui ne lui appartient pas • contrôle côté serveur (@PreAuthorize), jamais côté client
    Injection (SQL, LDAP, commandes) requêtes paramétrées, JPA ou PreparedStatement • jamais de concaténation de chaînes
    Cryptographic Failures données sensibles en clair ou mal protégées • TLS partout, BCrypt ou Argon2 pour les mots de passe
    Security Misconfiguration en-têtes de sécurité absents, stack traces exposées, endpoints Actuator ouverts en production
    Composants vulnérables dépendances obsolètes • OWASP Dependency-Check ou Snyk dans la CI
    SSRF le serveur appelle une URL fournie par l'utilisateur • liste blanche de domaines

    À quoi s'ajoutent XSS (échappement des sorties, Content-Security-Policy) et CSRF (jetons, activés par défaut dans Spring Security pour les sessions à cookies).

    → HTTP Security Headers · JWT Authentication Pattern · Cookie Security · Container Security

    15. DevOps et exploitation

    Image Docker multi-stage (build séparé du runtime), utilisateur non-root, image de base minimale, secrets par variables d'environnement — jamais dans l'image. Pipeline : build → tests → scan de vulnérabilités → image → déploiement. Le pull-based deployment évite de placer des identifiants de production dans la CI : c'est le serveur qui va chercher sa version.

    Observabilité, trois piliers : logs structurés en JSON portant un correlationId, métriques exposées par Actuator vers Prometheus/Grafana, traces distribuées pour suivre une requête à travers les services.

    Et le constat qui structure tout le travail de RUN : un serveur peut être vert sur tous les indicateurs d'infrastructure pendant que le service est rouge en applicatif, parce que tous les threads attendent une connexion en base. Descendre dans la stack jusqu'à la cause racine sans se laisser rassurer par les premiers tableaux de bord — c'est là que se joue la différence.

    → RUN, MCO et SRE · Investigation d'incidents • 4 patterns · CI/CD Pipeline Pattern

    Points d'attention

    • confondre IoC (le principe) et DI (le mécanisme)
    • croire que volatile rend le code thread-safe
    • laisser un état mutable dans un bean singleton
    • exposer une entité JPA dans le contrat d'API
    • traiter les erreurs dans chaque contrôleur au lieu de centraliser dans l'advice
    • mettre @SpringBootTest sur tous les tests
    • viser un pourcentage de couverture plutôt que couvrir les règles métier
    • placer la classe @SpringBootApplication hors de la racine du package applicatif

    Questions classiques

    Différence entre Spring et Spring Boot ?

    Le même conteneur IoC, pré-assemblé : auto-configuration conditionnelle, starters cohérents, serveur embarqué, configuration externalisée, Actuator. Boot ne remplace pas Spring, il l'assemble.

    Comment déclare-t-on un bean ?

    @Component / @Service / @Repository sur une classe qu'on possède • une méthode @Bean dans une @Configuration pour une classe de librairie.

    Différence entre @Component et @Service ?

    Aucune techniquement • @Service documente l'appartenance à la couche métier. Seul @Repository ajoute un comportement : la traduction d'exceptions d'accès aux données.

    Différence entre @Controller et @RestController ?

    @RestController = @Controller + @ResponseBody : il retourne les données sérialisées au lieu d'un nom de vue.

    Différence entre Repository et Service ?

    Le repository parle à la base et rien d'autre • le service porte les règles métier, orchestre plusieurs repositories et délimite la transaction.

    Qu'est-ce que l'exclusion mutuelle ?

    La garantie qu'un seul thread accède à une ressource partagée à la fois • synchronized, ReentrantLock, ou les classes atomiques.

    Qu'est-ce qu'un deadlock et comment l'éviter ?

    Deux threads se bloquent mutuellement, chacun attendant un verrou détenu par l'autre • acquérir les verrous toujours dans le même ordre, ou utiliser tryLock avec timeout.

    Héritage ou composition ?

    Composition par défaut • héritage seulement quand la relation « est un » est évidente et stable, car il crée un couplage fort avec l'implémentation du parent.

    Qu'est-ce que CQRS ?

    Séparer le modèle d'écriture du modèle de lecture, chacun optimisé pour son usage • au prix d'une cohérence éventuelle entre les deux.

    Comment fonctionne Spring Batch ?

    Un Job composé de Steps • chaque step lit, transforme et écrit par chunks avec commit toutes les N lignes, l'état étant persisté dans le JobRepository, ce qui rend le job redémarrable.

    Synthèse

    • Java : bytecode sur JVM, typage statique, GC • les versions LTS 17 et 21 structurent les projets actuels
    • Exceptions : Error ne se rattrape pas, checked ou unchecked est un choix de conception
    • Concurrence : distinguer atomicité, visibilité et interblocage • un singleton avec état est un bug en attente
    • Architecture : Controller adapte, Service décide, Repository accède • hexagonale et CQRS prolongent cette séparation
    • Patterns : les nommer, mais surtout savoir où ils vivent déjà dans Spring
    • Boot : auto-configuration conditionnelle qui s'efface devant les beans explicites
    • Tests : pyramide, tranches Spring, Testcontainers • la couverture ne mesure pas la qualité
    • Sécurité : contrôle d'accès côté serveur, requêtes paramétrées, dépendances scannées
    • RUN : logs corrélés, métriques, traces • et la capacité à descendre jusqu'à la cause racine
