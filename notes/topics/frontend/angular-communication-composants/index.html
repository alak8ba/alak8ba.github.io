    Angular • communication entre composants

    Complément détaillé de la section Component Communication des fondamentaux Angular : les six mécanismes, ce que chacun résout, et lequel choisir selon la relation entre les composants.

    Le critère de choix

    Tout se décide sur une seule question : quelle est la relation entre les deux composants ?

    flowchart TD
    Q{Relation entre les composants ?} -->|Parent vers enfant direct| A[Input]
    Q -->|Enfant vers parent direct| B[Output + EventEmitter]
    Q -->|Ancetre vers descendant lointain| C[Service, ou provide/inject]
    Q -->|Aucune relation d arborescence| D[Service partage avec RxJS ou signal]
    Q -->|Le parent pilote l enfant| E[ViewChild]
    Q -->|Etat qui survit a la navigation| F[Service racine, ou store]
    Mécanisme Relation Sens
    @Input() parent → enfant direct descendant
    @Output() + EventEmitter enfant → parent direct ascendant
    Service partagé n'importe quels composants multidirectionnel
    @ViewChild parent → enfant, en impératif descendant
    Projection de contenu (ng-content) parent injecte du contenu descendant
    Router (paramètres, state) entre pages selon la navigation

    1. @Input() et @Output() • le contrat direct

    // ENFANT : il declare ce qu'il recoit et ce qu'il emet
@Component({ selector: 'app-facture-carte', standalone: true, template: `
  <article (click)="selection.emit(facture)">
    <h3>{{ facture.reference }}</h3>
    <button (click)="valider.emit(facture.id); $event.stopPropagation()">Valider</button>
  </article>` })
export class FactureCarteComponent {
  @Input({ required: true }) facture!: Facture;   // required : erreur de compilation si absent
  @Output() selection = new EventEmitter<Facture>();
  @Output() valider   = new EventEmitter<string>();
}

    <!-- PARENT : [] pour ce qui descend, () pour ce qui remonte -->
<app-facture-carte
    [facture]="factureCourante"
    (selection)="ouvrir($event)"
    (valider)="validerFacture($event)" />

    La syntaxe, une bonne fois

    [propriete] : une valeur descend du parent vers l'enfant. (evenement) : un événement remonte de l'enfant vers le parent. [(ngModel)] : les deux à la fois - c'est visuellement « une boîte dans des parenthèses », d'où le surnom banana in a box.

    Les trois pièges des Input / Output

    • Muter l'objet reçu : un @Input() est une référence partagée. Modifier facture.montant dans l'enfant modifie l'objet du parent, sans que personne ne l'ait demandé. Un enfant lit son input et émet un événement pour demander un changement ; il ne décide pas.
    • EventEmitter hors d'un @Output() : ce n'est pas un bus de messages. Pour communiquer hors relation parent-enfant, c'est un service.
    • Chaîne trop longue : faire remonter un événement sur cinq niveaux (prop drilling) est le signal qu'il faut un service.

    La version moderne, en signals

    // Angular 17+ : meme contrat, mais reactif et mieux type
export class FactureCarteComponent {
  readonly facture   = input.required<Facture>();
  readonly selection = output<Facture>();
  readonly libelle   = computed(() => `Facture ${this.facture().reference}`);
}

    2. Le service partagé • le mécanisme qui résout le reste

    C'est le point à maîtriser : dès que deux composants ne sont pas dans une relation parent-enfant directe, la réponse est un service.

    À quoi sert réellement un service

    Un service n'est pas « la classe qui appelle l'API REST ». C'est l'unité injectable où l'on met tout ce qui ne dépend pas d'un écran :

    • l'accès aux données (API, cache, stockage)
    • l'état partagé entre composants
    • la logique métier réutilisable
    • la communication entre composants sans lien d'arborescence

    Avec providedIn: 'root', Angular n'en crée qu'une seule instance pour toute l'application : c'est précisément ce qui permet à deux composants éloignés de voir la même donnée.

    @Injectable({ providedIn: 'root' })         // singleton : une seule instance partagee
export class PanierService {

  // Source de verite, PRIVEE : personne ne peut pousser une valeur de l'exterieur
  private readonly _lignes = new BehaviorSubject<Ligne[]>([]);

  // Exposition en lecture seule
  readonly lignes$ = this._lignes.asObservable();
  readonly total$  = this.lignes$.pipe(
      map(lignes => lignes.reduce((t, l) => t + l.montant, 0)));

  ajouter(ligne: Ligne): void {
    this._lignes.next([...this._lignes.value, ligne]);   // nouvelle reference, pas de mutation
  }
}

    // Composant A : il ecrit
export class CatalogueComponent {
  private readonly panier = inject(PanierService);
  ajouter(article: Article) { this.panier.ajouter(Ligne.depuis(article)); }
}

// Composant B, ailleurs dans l'arbre : il lit, et se met a jour tout seul
@Component({ template: `<span>{{ total$ | async | currency:'EUR' }}</span>` })
export class EnteteComponent {
  readonly total$ = inject(PanierService).total$;
}

    Subject ou BehaviorSubject : la distinction qui compte

    Un Subject n'a pas de valeur courante : celui qui s'abonne après l'émission ne reçoit rien. Un BehaviorSubject garde la dernière valeur et la délivre immédiatement à tout nouvel abonné.

    Pour de l'état partagé, c'est toujours BehaviorSubject (ou un signal) - sinon un composant créé après coup affiche un écran vide jusqu'au prochain changement. Le Subject convient aux événements ponctuels : « l'utilisateur vient de se déconnecter ».

    → Observables et RxJS

    La même chose en signals

    @Injectable({ providedIn: 'root' })
export class PanierService {
  private readonly _lignes = signal<Ligne[]>([]);
  readonly lignes = this._lignes.asReadonly();
  readonly total  = computed(() => this._lignes().reduce((t, l) => t + l.montant, 0));

  ajouter(ligne: Ligne) { this._lignes.update(l => [...l, ligne]); }
}

    Plus court, pas d'abonnement à libérer, pas de pipe async. C'est la direction prise par Angular depuis la version 16 pour l'état synchrone ; RxJS reste indispensable pour les flux asynchrones - HTTP, WebSocket, événements combinés.

    3. @ViewChild • le parent pilote l'enfant

    @ViewChild(FormulaireComponent) formulaire!: FormulaireComponent;

ngAfterViewInit() {
  this.formulaire.reinitialiser();     // disponible seulement APRES le rendu de la vue
}

    À réserver aux actions impératives - donner le focus, réinitialiser, déclencher une animation. Utiliser @ViewChild pour lire des données que l'enfant détient est un signe que la donnée est au mauvais endroit : elle devrait descendre par @Input() ou vivre dans un service. → Cycle de vie d'un composant

    4. Ce qui n'est pas un canal de communication

    localStorage ne sert pas à faire communiquer des composants

    C'est l'erreur de conception la plus fréquente. localStorage est un stockage de persistance, pas un mécanisme réactif :

    • aucune réactivité : écrire une valeur ne prévient personne. L'autre composant ne se rafraîchit pas, il faudrait le relire en boucle
    • tout est chaîne : JSON.parse / stringify à chaque accès, sans typage
    • synchrone et bloquant, sur le thread de l'interface
    • partagé entre onglets, donc source de bugs inattendus
    • lisible par tout script de la page : jamais de jeton d'authentification

    Son usage légitime : survivre à un rechargement de page - préférence de thème, brouillon de formulaire, dernier filtre utilisé. L'état applicatif vivant, lui, appartient à un service.

    → HTML vs HTML5 • stockage côté client · Cookie Security

    // Le bon usage : le service reste la source de verite, localStorage n'est qu'une SAUVEGARDE
@Injectable({ providedIn: 'root' })
export class PreferencesService {
  private readonly _theme = signal<Theme>(this.lire());
  readonly theme = this._theme.asReadonly();

  changer(theme: Theme) {
    this._theme.set(theme);                                  // 1. l'etat reactif : tout se met a jour
    try { localStorage.setItem('theme', theme); } catch {}   // 2. la persistance, best effort
  }

  private lire(): Theme {
    try { return (localStorage.getItem('theme') as Theme) ?? 'clair'; } catch { return 'clair'; }
  }
}
    Besoin Le bon outil
    État partagé vivant service (BehaviorSubject ou signal)
    Survivre à un rechargement localStorage, alimenté par le service
    Limité à l'onglet sessionStorage
    État complexe, nombreuses actions, traçabilité un store → NgRx
    État lié à l'URL (filtres, pagination) les paramètres de route - partageables et restaurables

    Questions typiques, réponses courtes

    « Comment un composant parent communique-t-il avec son enfant ? » Par @Input() : le parent lie une valeur avec [propriete], et l'enfant la reçoit. Dans l'autre sens, l'enfant déclare un @Output() avec un EventEmitter et émet ; le parent écoute avec (evenement). Le sens est toujours le même : les données descendent, les événements remontent.

    « Et entre deux composants sans lien de parenté ? » Par un service partagé, injecté avec providedIn: 'root' - une seule instance pour toute l'application. Le service détient l'état dans un BehaviorSubject ou un signal, l'expose en lecture seule, et chaque composant s'y abonne. C'est ce qui évite de faire remonter un événement sur cinq niveaux.

    « À quoi sert un service ? » Pas seulement à appeler une API. C'est l'unité injectable qui porte tout ce qui n'appartient pas à un écran : accès aux données, état partagé, logique métier réutilisable, et communication entre composants éloignés. Le fait qu'il soit singleton est ce qui rend le partage possible.

    « Subject ou BehaviorSubject ? » BehaviorSubject pour de l'état : il conserve la dernière valeur et la donne immédiatement à tout nouvel abonné. Subject pour un événement ponctuel, où arriver en retard signifie qu'il n'y a rien à recevoir.

    « Peut-on utiliser localStorage pour faire communiquer deux composants ? » Non : il n'est pas réactif, écrire une valeur ne notifie personne. C'est un moyen de persistance, utile pour survivre à un rechargement. L'état partagé vivant appartient à un service ; localStorage ne fait qu'en sauvegarder une copie.
