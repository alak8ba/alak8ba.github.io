    Migrations de schéma • Liquibase, Flyway et le déploiement sans coupure

    Contexte

    « Demain, on ajoute une colonne dans la table. Comment ça se passe ? »

    La question paraît anodine. Elle teste en réalité trois choses :

    1. le schéma est-il versionné avec le code, ou modifié à la main en production ?
    2. la modification est-elle rejouable sur tous les environnements, dans le même ordre ?
    3. l'application survit-elle au moment où deux versions du code tournent en même temps ?

    Sans outil de migration, le schéma dérive : la recette ne ressemble plus à la production, personne ne sait quel script a été passé où, et la reconstruction d'un environnement devient une enquête.

    Le principe

    Le schéma fait partie du code. Il est versionné dans le dépôt, appliqué automatiquement, et son historique est traçable - au même titre qu'une classe Java.

    Liquibase et Flyway

    Liquibase Flyway
    Format XML, YAML, JSON ou SQL SQL (et Java pour les cas complexes)
    Unité changeSet identifié par id + author fichier V<version>__<description>.sql
    Abstraction base oui : le même changelog génère le SQL de chaque SGBD non : le SQL est écrit pour une base
    Rollback déclaratif, parfois automatique payant / manuel selon l'édition
    Table de suivi DATABASECHANGELOG + DATABASECHANGELOGLOCK flyway_schema_history
    Courbe d'entrée plus riche, donc plus complexe très simple
    Terrain multi-SGBD, gros SI, besoin de rollback équipe qui assume son SQL

    Le critère de choix honnête : Flyway si l'équipe veut écrire du SQL et une seule base ; Liquibase si l'on a besoin d'abstraction multi-SGBD, de rollback déclaratif ou de contextes/labels par environnement. Les deux versionnent le schéma - c'est déjà 90 % du bénéfice.

    Comment Liquibase fonctionne

    flowchart LR
    APP[Demarrage de l application] --> LOCK[Prise du verrou DATABASECHANGELOGLOCK]
    LOCK --> READ[Lecture du changelog]
    READ --> CMP[Comparaison avec DATABASECHANGELOG]
    CMP --> RUN[Execution des changeSets manquants, dans l ordre]
    RUN --> TRACE[Insertion id + author + checksum]
    TRACE --> REL[Liberation du verrou]
    # db/changelog/db.changelog-master.yaml
databaseChangeLog:
  - include: { file: db/changelog/2026/001-creation-facture.yaml }
  - include: { file: db/changelog/2026/002-ajout-colonne-devise.yaml }

    # 002-ajout-colonne-devise.yaml
databaseChangeLog:
  - changeSet:
      id: 002-ajout-colonne-devise
      author: akouba
      changes:
        - addColumn:
            tableName: facture
            columns:
              - column: { name: devise, type: varchar(3) }   # NULLABLE au depart
      rollback:
        - dropColumn: { tableName: facture, columnName: devise }

    spring:
  liquibase:
    change-log: classpath:db/changelog/db.changelog-master.yaml
    enabled: true

    Trois règles non négociables :

    Un changeSet appliqué ne se modifie jamais

    Liquibase stocke une empreinte (checksum) de chaque changeSet exécuté. Modifier un changeSet déjà passé fait échouer le démarrage sur tous les environnements où il a été appliqué : checksum validation failed.

    La règle : on corrige en ajoutant un nouveau changeSet, jamais en éditant l'ancien. (clearCheckSums existe, mais c'est un aveu : on masque l'historique réel.)

    • un changeSet = un changement atomique : pas dix modifications dans le même bloc
    • toujours écrire le rollback, même quand il paraît évident
    • jamais de modification manuelle en production : sinon l'historique ment

    La vraie question • ajouter une colonne sans coupure

    C'est là que la réponse se joue. Pendant un déploiement progressif, l'ancienne et la nouvelle version du code tournent en même temps sur des instances différentes.

    flowchart TD
    subgraph T1[Pendant le deploiement]
      V1[Instances en version N] --> DB[(Base : un seul schema)]
      V2[Instances en version N+1] --> DB
    end

    Conséquence : le schéma doit être compatible avec les deux versions du code, simultanément.

    La règle : expand / contract

    flowchart LR
    E[1. EXPAND<br/>ajouter, sans rien casser] --> M[2. MIGRATE<br/>remplir et doubler les ecritures]
    M --> C[3. CONTRACT<br/>supprimer l ancien, plus tard]
    Étape Livraison Ce qu'on fait
    Expand N+1 ajouter la colonne nullable, ou avec valeur par défaut. L'ancien code l'ignore, il ne la voit pas
    Migrate N+1 puis N+2 remplir les lignes existantes par lots ; le code écrit dans l'ancien et le nouveau champ
    Contract N+3, des semaines plus tard quand plus personne ne lit l'ancien : NOT NULL, suppression de l'ancienne colonne

    Ce qui est sûr, et ce qui casse

    Opération Sans coupure ? Pourquoi
    Ajouter une colonne nullable oui l'ancien code l'ignore
    Ajouter une colonne NOT NULL sans défaut non les INSERT de l'ancien code échouent
    Ajouter une colonne NOT NULL avec défaut oui sur PostgreSQL récent valeur par défaut sans réécriture de table
    Ajouter un index oui avec CONCURRENTLY sinon la table est verrouillée en écriture
    Renommer une colonne non rupture immédiate pour l'une des deux versions
    Supprimer une colonne non, tant que l'ancien code la lit à faire en phase contract
    Changer un type non en général réécriture de table + incompatibilité de code
    Ajouter une contrainte oui en deux temps NOT VALID puis VALIDATE CONSTRAINT

    Renommer une colonne n'existe pas, en réalité

    Un renommage sans coupure est toujours une séquence en trois livraisons : ajouter la nouvelle colonne, écrire dans les deux, migrer les données, basculer les lectures, puis supprimer l'ancienne. Un RENAME COLUMN direct casse la version du code qui tourne encore à côté.

    Le verrou qui fait tomber la production

    Sur une grosse table, ALTER TABLE prend un verrou exclusif. Même rapide, il attend derrière les transactions en cours - et toutes les requêtes suivantes attendent derrière lui. Le symptôme : l'application se fige d'un coup pendant une migration « anodine ».

    Les réponses : lock_timeout court, index en CONCURRENTLY, remplissage par lots, et migration en heures creuses sur les tables volumineuses.

    Migrations et déploiement

    Approche Principe Remarque
    Au démarrage de l'application Liquibase s'exécute avant l'ouverture du service simple ; attention au démarrage de N instances en parallèle - le verrou les sérialise
    Étape dédiée de la CI/CD un job applique les migrations, puis on déploie plus contrôlable, recommandé dès qu'il y a plusieurs instances
    Manuellement un DBA passe les scripts dérive garantie entre environnements 
    # Verifier ce qui SERAIT applique, sans rien appliquer
mvn liquibase:status
mvn liquibase:updateSQL      # genere le SQL pour relecture / validation DBA

    La chaîne saine : les migrations sont jouées en CI sur une base jetable (Testcontainers), et relues comme du code. Une migration non testée est une mise en production non testée. → Testcontainers · CI/CD Pipeline Pattern

    Pièges classiques

    Piège Conséquence Correction
    Modifier un changeSet déjà appliqué échec de démarrage partout nouveau changeSet
    hibernate.ddl-auto=update en production le schéma évolue implicitement, sans historique validate en production, migrations explicites
    Ajout NOT NULL sans défaut les écritures de l'ancien code échouent nullable d'abord, contrainte plus tard
    Index créé sans CONCURRENTLY table verrouillée, production figée CREATE INDEX CONCURRENTLY
    Verrou Liquibase resté pris (processus tué) les instances suivantes attendent indéfiniment libérer DATABASECHANGELOGLOCK après diagnostic
    Migration de données massive dans un changeSet transaction énorme, verrous longs traitement par lots, hors migration de schéma
    Rollback jamais testé inutilisable le jour où il faut le tester en recette

    Questions typiques, réponses courtes

    « Comment ajoutez-vous une colonne demain ? » Un changeSet Liquibase versionné avec le code, colonne nullable ou avec valeur par défaut, appliqué par la CI avant le déploiement. La colonne est ignorée par la version précédente du code, qui tourne encore pendant la bascule. Si elle doit devenir obligatoire, c'est une livraison ultérieure : remplissage des lignes existantes, puis contrainte.

    « Pourquoi pas ddl-auto=update ? » Parce qu'il modifie le schéma implicitement, sans historique, sans ordre garanti et sans rollback - et qu'il ne fait jamais ce qu'on croit sur un renommage ou une suppression. En production, validate : l'application vérifie que le schéma correspond, et refuse de démarrer sinon.

    « Liquibase ou Flyway ? » Flyway si l'équipe assume son SQL sur une seule base : plus simple. Liquibase pour l'abstraction multi-SGBD, le rollback déclaratif et les contextes par environnement. Les deux répondent au besoin principal : versionner le schéma avec le code.

    « Comment renommer une colonne sans coupure ? » On ne renomme pas : on ajoute la nouvelle, on écrit dans les deux, on migre les données, on bascule les lectures, puis on supprime l'ancienne quand plus personne ne la lit. Trois livraisons, parce que deux versions du code cohabitent pendant chaque déploiement.

    « Qui applique les migrations en production ? » La chaîne de livraison, pas une personne. Étape dédiée avant le déploiement, SQL relu en revue, migrations jouées en CI sur une base jetable. Une modification manuelle en production fait mentir l'historique et rend les environnements non reproductibles.
