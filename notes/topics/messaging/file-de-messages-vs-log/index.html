    File de messages ou log distribué • les deux modèles

    Contexte

    « Broker de messages » désigne deux familles de produits qui n'ont ni le même modèle, ni les mêmes garanties, ni les mêmes usages :

    • les files de messages - ActiveMQ, RabbitMQ, IBM MQ, Azure Service Bus, SQS
    • les logs distribués - Kafka, Pulsar, Redpanda

    Les comparer sur les performances rate l'essentiel. La différence est structurelle, et une seule phrase la résume :

    La distinction fondatrice

    Dans une file, un message consommé disparaît. Dans un log, un message lu reste.

    Une file est un tuyau : elle transporte, puis oublie. Un log est un registre : il conserve, et chaque lecteur mémorise où il en est.

    Tout le reste - rejeu, fan-out, ordre, montée en charge, supervision - découle de là.

    Les deux modèles, côte à côte

    flowchart LR
    subgraph FILE[File de messages]
      P1[Producteur] --> Q[(File)]
      Q -->|message retire| C1[Consommateur A]
      Q -->|message retire| C2[Consommateur B]
    end
    subgraph LOG[Log distribue]
      P2[Producteur] --> L[(Log : messages conserves)]
      L -->|offset 42| G1[Groupe A]
      L -->|offset 17| G2[Groupe B]
    end
    File de messages Log distribué
    Après lecture le message est supprimé le message reste jusqu'à expiration
    Position de lecture connue du broker de chaque consommateur (offset)
    Rejouer l'historique impossible natif : on repositionne l'offset
    Plusieurs usages du même flux il faut dupliquer le message par destination un nouveau groupe de consommateurs, sans rien changer
    Accusé de réception par message (ack / nack) par offset commité
    Reprise d'un message en échec redélivrance native, puis DLQ à construire : retry, DLT
    Routage riche : sujets, en-têtes, filtres, priorités par partition, via la clé
    Ordre par file, fragile dès plusieurs consommateurs strict par partition
    Priorités, TTL par message oui non
    Débit typique milliers à dizaines de milliers/s centaines de milliers à millions/s
    Rétention quelques minutes à quelques heures jours, semaines, ou infinie
    Modèle mental boîte aux lettres journal comptable

    Les deux schémas de distribution

    Ils existent dans les deux familles, mais portent des noms différents - c'est la première source de confusion.

    Point à point • un seul consommateur traite

    flowchart LR
    P[Producteur] --> Q[(Queue)]
    Q --> C1[Instance 1]
    Q -.->|ne recoit pas ce message| C2[Instance 2]
    Q -.-> C3[Instance 3]

    Plusieurs instances lisent la même file pour répartir la charge : chaque message n'est traité qu'une fois. C'est le pattern competing consumers.

    Famille Comment
    JMS / AMQP plusieurs consommateurs sur la même Queue
    Kafka plusieurs instances dans le même group.id

    Publication / abonnement • tout le monde reçoit

    flowchart LR
    P[Producteur] --> T[(Topic)]
    T --> A[Facturation]
    T --> B[Analytique]
    T --> C[Notification]
    Famille Comment
    JMS une Topic, avec abonnements durables si l'on veut survivre à une déconnexion
    AMQP / RabbitMQ un exchange fanout ou topic, une queue par consommateur
    Kafka un group.id différent par usage - et la rétention rend l'abonnement durable par construction

    Le faux ami : le mot « topic »

    En JMS, une Topic diffuse à tous les abonnés connectés, et le message disparaît ensuite. En Kafka, un topic est un log conservé, partitionné, que l'on relit.

    Même mot, deux objets différents. Dire « un topic Kafka, c'est comme un topic JMS » est faux : le rapprochement correct est topic Kafka lu par N groupes ≈ topic JMS avec abonnements durables, mais sans rétention ni rejeu côté JMS.

    Ce que chaque modèle fait mieux

    La file est meilleure pour

    Besoin Pourquoi
    Répartir des tâches entre des travailleurs c'est exactement son modèle : une tâche, un exécutant
    Routage complexe par en-tête, par motif, par filtre - sans que le producteur connaisse les destinataires
    Priorités un message urgent passe devant
    Reprise fine par message redélivrance, compteur de tentatives, DLQ native
    Requête / réponse ReplyTo et corrélation sont dans le standard
    Volumes modérés, latence faible pas de partitionnement à dimensionner
    TTL par message expiration individuelle

    Le log est meilleur pour

    Besoin Pourquoi
    Plusieurs consommateurs du même flux ajouter un usage ne touche pas le producteur
    Rejouer l'historique reconstruire une projection, corriger un traitement
    Très gros débits partitionnement horizontal
    Ordre garanti par entité une clé, une partition
    Historique des faits le log est la source de vérité des événements
    Consommateurs lents ou arrêtés ils rattrapent, rien n'est perdu

    La grille de choix, en une ligne

    Une tâche à faire faire → file. Un fait à raconter → log.

    « Envoyer cet e-mail », « générer ce PDF », « traiter ce virement » : ce sont des commandes, adressées à un destinataire unique - une file suffit et coûte moins cher.

    « La commande a été validée » : c'est un fait, qui intéresse potentiellement plusieurs services, aujourd'hui et demain - c'est un log.

    Le point qui tranche vraiment : le rejeu

    C'est l'argument à donner quand on doit justifier un choix, parce qu'il est impossible à contourner.

    • File : le message consommé n'existe plus. Un bug dans le traitement, et la donnée est perdue - sauf si elle a été sauvegardée ailleurs avant. Corriger le code ne ramène rien.
    • Log : le message est toujours là. On corrige, on repositionne l'offset, on rejoue.
    # Rejouer l'integralite d'un topic dans une NOUVELLE projection
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group projection-v2 --topic commandes --reset-offsets --to-earliest --execute

    Conséquence directe sur l'architecture : un système dont les projections ou les read models peuvent devoir être reconstruits a besoin d'un log. Une file ne le permettra jamais. → CQRS · Read Models

    Ce qui est commun aux deux

    Les problèmes de fond ne dépendent pas du produit. Changer de broker ne les supprime pas :

    Problème Vrai partout
    Livraison au moins une fois le traitement doit être idempotent dans les deux cas
    Double écriture base + broker l'outbox est la réponse, quel que soit le broker
    Messages toxiques il faut une DLQ / DLT et quelqu'un qui la regarde
    Cohérence éventuelle l'asynchronisme la crée, le produit n'y change rien
    Ordre jamais garanti globalement, dans aucune des deux familles
    Supervision profondeur de file ou décalage de consommation : la métrique n°1

    → Idempotent Consumers · Outbox Pattern · Retry and DLT

    L'erreur d'architecture la plus coûteuse

    Choisir Kafka pour un besoin de file - répartir des tâches entre travailleurs, avec priorités et reprise unitaire - oblige à réimplémenter à la main ce qu'un broker de files fournit d'origine : redélivrance par message, DLQ, priorités, TTL.

    L'inverse est pire : choisir une file pour un besoin de log condamne à ne jamais pouvoir rejouer, et à dupliquer le message autant de fois qu'il y a de consommateurs.

    Et les modèles hybrides

    La frontière s'estompe : les produits de files ajoutent des mécanismes de log.

    Produit Mécanisme de type log
    RabbitMQ Streams log persistant, relecture par offset, en plus des queues classiques
    ActiveMQ Artemis rétention et relecture sur certaines configurations
    Pulsar log + files unifiés dans le même produit
    NATS JetStream flux persistant avec relecture

    Le modèle mental reste valable : la question n'est pas « quel produit », mais « ai-je besoin d'un tuyau ou d'un registre ? ». Le produit vient après.

    Questions typiques, réponses courtes

    « Quelle différence entre un broker de messages et Kafka ? » Le devenir du message. Dans une file, il est supprimé dès qu'il est consommé, et c'est le broker qui suit la progression. Dans un log, il est conservé selon une rétention, et chaque consommateur garde sa propre position. D'où le rejeu, le fan-out sans impact sur le producteur, et l'ordre par partition - qu'une file ne peut pas offrir.

    « Quand choisir une file plutôt qu'un log ? » Quand il s'agit de faire exécuter une tâche par un destinataire unique, avec du routage, des priorités, une reprise unitaire et une DLQ prête à l'emploi. Et quand les volumes ne justifient pas un cluster Kafka.

    « Point à point ou publication / abonnement ? » Point à point pour répartir la charge : un message, un traitant - c'est le pattern competing consumers. Publication / abonnement quand plusieurs usages différents ont besoin du même message. Les deux existent dans les deux familles, sous des noms différents.

    « Un topic JMS et un topic Kafka, c'est pareil ? » Non. Un topic JMS diffuse aux abonnés puis oublie ; un topic Kafka conserve et se relit. Même mot, deux objets - c'est une confusion fréquente et coûteuse en conception.

    « Peut-on rejouer un message dans une file ? » Non, une fois consommé il n'existe plus. On peut au mieux le republier si on l'a sauvegardé soi-même avant traitement. C'est l'argument décisif quand des projections doivent pouvoir être reconstruites.
