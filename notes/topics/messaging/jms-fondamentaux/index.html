    JMS • le standard Java de messagerie

    Contexte

    JMS (Jakarta Messaging, anciennement Java Message Service) est une API, pas un produit. C'est la distinction à poser en premier : JMS spécifie comment un programme Java parle à un broker, sans dire lequel.

    flowchart LR
    APP[Application Java] --> API[API JMS - standard]
    API --> AMQ[ActiveMQ Artemis]
    API --> IBM[IBM MQ]
    API --> WL[WebLogic / WildFly]
    API --> SQS[SQS via adaptateur]

    L'intérêt : changer de broker ne change pas le code applicatif. La limite : le standard ne couvre que le dénominateur commun - configuration, exploitation et particularités de chaque broker restent propriétaires.

    Le changement de nom qui casse les compilations

    javax.jms est devenu jakarta.jms avec Jakarta EE 9. C'est le même changement de namespace que pour le reste de l'écosystème : mécanique, mais il impose que toutes les librairies impliquées aient une version Jakarta. → Spring Boot 2 → 3

    Les objets du modèle

    Objet Rôle
    ConnectionFactory fabrique de connexions - le point de configuration
    Connection connexion au broker
    Session contexte de travail : transaction, mode d'accusé de réception
    Destination où l'on écrit ou lit : Queue ou Topic
    MessageProducer / JMSProducer émission
    MessageConsumer / JMSConsumer réception
    Message l'enveloppe : en-têtes, propriétés, corps

    Queue ou Topic

    Queue - point à point Topic - publication / abonnement
    Destinataires un seul consommateur traite le message tous les abonnés le reçoivent
    Plusieurs instances répartissent la charge (competing consumers) chacune reçoit une copie
    Consommateur absent le message attend dans la file le message est perdu, sauf abonnement durable
    Usage faire exécuter une tâche diffuser une information

    L'abonnement durable

    Sur une Topic, un abonné déconnecté rate les messages publiés pendant son absence. L'abonnement durable (durable subscriber, identifié par un nom stable) demande au broker de les conserver jusqu'au retour de l'abonné.

    C'est l'équivalent le plus proche de la persistance d'un log - mais sans rejeu de l'historique déjà consommé. → File de messages ou log distribué

    Les types de message

    Type Corps
    TextMessage chaîne - le plus utilisé, souvent du JSON
    BytesMessage binaire
    MapMessage paires clé / valeur
    ObjectMessage objet Java sérialisé
    StreamMessage flux de valeurs typées

    ObjectMessage : à éviter

    La sérialisation Java native couple producteur et consommateur à la même classe, avec le même serialVersionUID : toute évolution du modèle casse l'autre bout. Et désérialiser un objet venant du réseau est une faille connue d'exécution de code.

    TextMessage avec du JSON, et un contrat explicite, règle les deux problèmes.

    JMS est-il asynchrone ?

    Oui sur le principe, mais le mot recouvre trois choses différentes - et les confondre mène à de mauvaises conceptions.

    1. Architecturalement : oui

    Le producteur dépose son message et repart. Il n'attend ni le traitement, ni même que le consommateur soit démarré. C'est le découplage temporel, la raison d'être de la messagerie.

    2. À la réception : les deux modes coexistent

    Mode Code Nature
    Synchrone (pull) Message m = consumer.receive(5000); bloquant : le thread attend un message, ou le délai
    Asynchrone (push) setMessageListener(...), @JmsListener le broker pousse, le conteneur invoque la méthode 
    // Synchrone : le thread reste bloque jusqu'a un message ou l'expiration du delai
Message message = consumer.receive(5000);

// Asynchrone : c'est le conteneur qui appelle, sur son propre thread
@JmsListener(destination = "factures")
public void onMessage(FactureMessage facture) { service.traiter(facture); }

    3. À l'émission : send() bloque souvent

    Pour un message persistant, send() attend l'accusé du broker - aller-retour réseau et écriture disque comprises. JMS 2.0 permet de ne pas attendre :

    producer.setAsync(true);                       // ou send(..., new CompletionListener() {...})

    Asynchrone n'est pas non bloquant

    C'est la distinction qui compte. Un @JmsListener est asynchrone du point de vue de l'architecture, mais son traitement s'exécute sur un thread bloqué du début à la fin. Le réglage concurrency fixe le nombre de ces threads, donc le parallélisme réel.

    Ce n'est pas un modèle réactif : c'est un thread par consommateur, qui attend. Sur des traitements longs, c'est le nombre de threads - et non le broker - qui borne le débit.

    Le cas qui brouille tout : request-reply

    JmsTemplate.sendAndReceive - file temporaire plus JMSCorrelationID - donne à l'appelant une apparence synchrone : il bloque jusqu'à la réponse. Le transport, lui, reste asynchrone.

    C'est utile pour faire dialoguer deux systèmes qui ne parlent que messages, mais cela réintroduit le couplage temporel qu'on cherchait à éviter : si le répondeur est arrêté, l'appelant attend puis expire. Quand une réponse immédiate est nécessaire, un appel HTTP est plus simple et plus lisible. → Synchronous Vs Asynchronous

    Accusés de réception et transactions

    C'est le cœur du sujet : qui décide qu'un message est traité, et quand.

    Mode Quand le message est acquitté Conséquence
    AUTO_ACKNOWLEDGE à la réception, avant le traitement métier une erreur → message perdu
    CLIENT_ACKNOWLEDGE quand le code appelle message.acknowledge() le contrôle est explicite
    DUPS_OK_ACKNOWLEDGE acquittement paresseux plus rapide, doublons assumés
    Session transactée au commit() de la session tout ou rien sur un lot 
    // Session transactee : consommation et production dans la meme unite
Session session = connection.createSession(true, Session.SESSION_TRANSACTED);
try {
    Message message = consumer.receive(1000);
    traiter(message);
    producer.send(reponse);
    session.commit();          // le message consomme ET la reponse produite
} catch (Exception e) {
    session.rollback();        // le message retourne dans la file
}

    La transaction JMS ne couvre pas la base de données

    Comme pour Kafka, l'atomicité s'arrête au broker. Une transaction JMS et une transaction base sont deux transactions distinctes.

    Le XA / 2PC existe côté JMS - c'est même son argument historique - mais il coûte cher : coordinateur de transactions, verrous longs, transactions en doute à débloquer manuellement. En pratique, on préfère aujourd'hui at-least-once + traitement idempotent, ou l'outbox. → Outbox Pattern · Idempotent Consumers · Transactions Kafka

    Redélivrance et file de rebut

    Le mécanisme que JMS fournit d'origine, et que Kafka oblige à construire :

    Traitement en echec
  → le message retourne dans la file
  → redelivre (JMSRedeliveryCount incremente, delai croissant)
  → apres N tentatives : deplacé dans la Dead Letter Queue

    @JmsListener(destination = "factures")
public void traiter(TextMessage message) throws JMSException {
    if (message.getIntProperty("JMSXDeliveryCount") > 1) {
        log.warn("redelivrance n°{}", message.getIntProperty("JMSXDeliveryCount"));
    }
    // une exception qui remonte = pas d'acquittement = redelivrance
}

    Le nombre de tentatives, le délai et la file de rebut se configurent côté broker - c'est là que le standard s'arrête et que le produit reprend la main.

    Sélecteurs • filtrer côté broker

    // Le consommateur ne recoit que ce qui l'interesse : le filtre s'applique AVANT l'envoi
consumer = session.createConsumer(queue, "type = 'URGENT' AND montant > 1000");

    message.setStringProperty("type", "URGENT");
message.setDoubleProperty("montant", 1500.0);

    La syntaxe est un sous-ensemble de SQL-92, appliqué aux propriétés du message, jamais au corps. C'est une capacité que Kafka n'a pas : côté log, tout consommateur lit tout et filtre lui-même.

    Le coût caché des sélecteurs

    Un sélecteur trop restrictif laisse s'accumuler dans la file les messages que personne ne prend. La file grossit sans qu'aucune erreur n'apparaisse - jusqu'à saturation du broker. Tout message doit avoir un preneur.

    Côté Spring

    spring:
  jms:
    listener:
      acknowledge-mode: auto        # ou client
      concurrency: 3-10             # nombre de consommateurs concurrents
    template:
      delivery-mode: persistent     # survit au redemarrage du broker
      receive-timeout: 5s
  activemq:
    broker-url: tcp://broker:61616

    @Component
public class FactureListener {

    @JmsListener(destination = "factures", concurrency = "3-10")
    public void onMessage(FactureMessage facture) {     // conversion automatique
        service.traiter(facture);                        // exception = redelivrance
    }
}

@Service
public class FactureEmetteur {

    private final JmsTemplate jmsTemplate;

    public void emettre(Facture facture) {
        jmsTemplate.convertAndSend("factures", facture, message -> {
            message.setStringProperty("type", facture.urgence());
            return message;
        });
    }
}

    Quatre réglages qui comptent en production :

    Réglage Effet
    delivery-mode: persistent le message est écrit sur disque : il survit au redémarrage du broker
    concurrency nombre de consommateurs en parallèle - c'est le levier de débit
    acknowledge-mode auto acquitte avant le métier : perte possible en cas d'erreur
    sessionTransacted acquittement lié au succès du traitement

    Persistant ou non : l'arbitrage

    Un message non persistant reste en mémoire : très rapide, perdu si le broker redémarre. Un message persistant est écrit sur disque avant acquittement au producteur : plus lent, mais il survit.

    Pour un ordre de paiement, persistant sans discussion. Pour un rafraîchissement d'affichage, non persistant est un choix légitime.

    Ce que JMS ne couvre pas

    Absent du standard Conséquence
    Configuration du broker files, DLQ, seuils : propriétaire
    Haute disponibilité, réplication propre à chaque produit
    Supervision métriques et outillage spécifiques
    Interopérabilité non-Java JMS est une API Java ; pour parler à d'autres langages, c'est AMQP ou MQTT qui font protocole

    C'est la nuance à retenir : JMS normalise l'API, AMQP normalise le protocole réseau. Un client .NET ne peut pas utiliser JMS ; il peut parler AMQP au même broker. → RabbitMQ et ActiveMQ

    Questions typiques, réponses courtes

    « Qu'est-ce que JMS ? » Une API Java standard pour dialoguer avec un broker de messages. Elle définit les objets - ConnectionFactory, Session, Queue, Topic, Message - sans imposer de produit. Le code applicatif reste le même que le broker soit ActiveMQ, IBM MQ ou un autre.

    « Queue ou Topic ? » Une Queue pour le point à point : un seul consommateur traite le message, et plusieurs instances se répartissent la charge. Une Topic pour la diffusion : tous les abonnés reçoivent une copie - avec abonnement durable si l'abonné doit pouvoir être déconnecté.

    « Comment garantit-on qu'un message n'est pas perdu ? » Message persistant, acquittement après le traitement - session transactée ou mode client, jamais AUTO_ACKNOWLEDGE sur un traitement critique - redélivrance en cas d'erreur, et file de rebut au-delà de N tentatives. La contrepartie : des doublons possibles, donc un traitement idempotent.

    « JMS est-il synchrone ou asynchrone ? » Asynchrone par nature : le producteur dépose et repart, sans attendre le consommateur. Mais l'API offre les deux modes de réception - receive() est un appel bloquant, alors qu'un MessageListener ou un @JmsListener est en mode poussé. Et asynchrone ne veut pas dire non bloquant : un listener occupe un thread pendant tout son traitement, c'est concurrency qui fixe le parallélisme réel.

    « JMS ou AMQP ? » JMS est une API, AMQP est un protocole réseau. JMS n'existe qu'en Java ; AMQP permet à des clients de n'importe quel langage de parler au même broker. Les deux coexistent : ActiveMQ Artemis expose à la fois une implémentation JMS et le protocole AMQP.

    « JMS ou Kafka ? » Ce n'est pas le même modèle. JMS s'adresse à des files où le message consommé disparaît, avec routage, priorités, redélivrance et DLQ d'origine. Kafka est un log conservé, relisible, à très fort débit. Une tâche à faire exécuter → file ; un fait à diffuser et rejouer → log.
