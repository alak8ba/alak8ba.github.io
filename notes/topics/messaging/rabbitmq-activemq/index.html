    RabbitMQ et ActiveMQ • les deux brokers de files

    Contexte

    Ce sont les deux brokers de files les plus répandus dans l'écosystème Java. Ils répondent au même besoin - transporter des messages vers un destinataire - mais leur modèle de routage diffère, et c'est ce qui guide le choix.

    RabbitMQ ActiveMQ
    Origine Erlang / OTP Java, fondation Apache
    Protocole natif AMQP 0-9-1 ouvert : OpenWire, AMQP, MQTT, STOMP
    JMS via un client dédié natif - c'est son terrain
    Modèle de routage exchange → binding → queue destination directe (Queue / Topic)
    Versions une seule ligne de produit Classic (historique) et Artemis (moderne)
    Interface d'admin très aboutie correcte
    Terrain typique polyglotte, routage riche, microservices SI Java, applications d'entreprise, JEE

    ActiveMQ : Classic ou Artemis

    Deux produits distincts sous le même nom. Artemis est la génération actuelle - architecture non bloquante, meilleures performances, base d'un serveur JEE. Classic est la branche historique, encore très présente dans les SI existants.

    C'est la première chose à vérifier sur un projet : configuration, outillage et caractéristiques ne sont pas les mêmes.

    Le modèle de RabbitMQ • la vraie différence

    Chez RabbitMQ, le producteur ne publie jamais dans une file. Il publie dans un exchange, qui décide de la distribution selon les bindings.

    flowchart LR
    P[Producteur] -->|routing key : facture.creee| EX[Exchange topic]
    EX -->|facture.*| Q1[(Queue facturation)]
    EX -->|facture.creee| Q2[(Queue notification)]
    EX -->|#| Q3[(Queue audit)]
    Q1 --> C1[Consommateur]
    Q2 --> C2[Consommateur]
    Q3 --> C3[Consommateur]

    Cette indirection est l'atout du produit : le producteur ignore qui écoute. Ajouter un consommateur, c'est créer une file et la lier à l'exchange - sans toucher au producteur.

    Type d'exchange Distribution
    direct clé de routage exactement égale
    topic motif avec jokers : facture.*, commande.#
    fanout toutes les files liées, la clé est ignorée
    headers selon les en-têtes plutôt que la clé 
    @Bean TopicExchange factureExchange() { return new TopicExchange("factures"); }
@Bean Queue notificationQueue()       { return QueueBuilder.durable("notification")
                                              .deadLetterExchange("dlx").build(); }
@Bean Binding binding(Queue q, TopicExchange ex) {
    return BindingBuilder.bind(q).to(ex).with("facture.creee");
}

    @RabbitListener(queues = "notification")
public void onFactureCreee(FactureMessage message) {
    service.notifier(message);          // exception = rejet, puis DLX selon la config
}

    Les mécanismes à connaître

    Prefetch • le réglage le plus impactant

    spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 10          # messages envoyes d'avance a CHAQUE consommateur
        concurrency: 3
        max-concurrency: 10

    Le broker pousse jusqu'à prefetch messages non acquittés vers un consommateur. Conséquence directe :

    • prefetch élevé : débit maximal, mais un consommateur lent accapare des messages que d'autres auraient pu traiter, et la répartition devient déséquilibrée
    • prefetch = 1 : répartition parfaitement équitable, débit plus faible - le bon réglage quand les traitements sont longs et de durées inégales

    C'est le premier paramètre à regarder quand « une instance travaille et les autres attendent ».

    Dead Letter Exchange et durée de vie

    QueueBuilder.durable("factures")
    .deadLetterExchange("dlx")          // ou vont les messages rejetes
    .deadLetterRoutingKey("facture.echec")
    .ttl(60_000)                        // expiration apres 60 s
    .maxLength(100_000)                 // au-dela, les plus anciens partent en DLX
    .build();

    Un message part en DLX quand il est rejeté sans remise en file, quand il expire, ou quand la file est pleine. C'est le mécanisme de reprise natif - celui qu'il faut construire soi-même côté Kafka. → Retry and DLT

    Le retard programmé, sans planificateur

    Une file avec un TTL et un DLX pointant vers la file de traitement produit un délai de réessai sans aucun composant supplémentaire : le message attend son expiration, puis est routé vers le traitement. C'est le motif classique du retry à délai croissant en RabbitMQ.

    Fiabilité côté production

    Mécanisme Ce qu'il garantit
    publisher confirms le broker accuse réception de la publication
    mandatory signale un message qu'aucune file n'a accepté - sinon il est perdu en silence
    file durable + message persistent survit au redémarrage du broker
    quorum queues réplication fondée sur Raft - le défaut recommandé en cluster

    Les deux pièges qui font perdre des messages sans erreur

    Sans publisher confirms, une publication est un envoi sans accusé : si le broker tombe à cet instant, le message n'existe nulle part et l'application n'en sait rien.

    Sans mandatory, un message dont la clé de routage ne correspond à aucun binding est silencieusement jeté. Une faute de frappe dans une clé de routage suffit - et rien dans les logs ne le signale.

    RabbitMQ Streams

    Depuis la version 3.9, RabbitMQ propose aussi des streams : un log persistant, relisible par offset, à côté des queues classiques. Le produit couvre donc les deux modèles - mais sur les très gros volumes, l'écosystème Kafka reste plus outillé. → File de messages ou log distribué

    Haute disponibilité

    RabbitMQ ActiveMQ Artemis
    Mécanisme quorum queues (Raft) ; les mirrored queues sont obsolètes paires live / backup, réplication ou stockage partagé
    Nombre de nœuds 3 ou 5 - une majorité est nécessaire paire, ou groupes de paires
    Partition réseau politique à choisir (pause_minority recommandé) détection et bascule
    Montée en charge sharding applicatif, plusieurs files clustering avec redistribution des messages

    Une file reste portée par un nœud

    Contrairement à une partition Kafka répartie sur plusieurs brokers, une file RabbitMQ a un nœud leader. Une file unique ne s'étale pas sur le cluster : le parallélisme vient du nombre de consommateurs, et la montée en charge au-delà d'un nœud impose de découper en plusieurs files.

    C'est la limite structurelle qui décide du passage à un log quand les volumes montent.

    Choisir

    Situation Choix raisonnable
    Routage riche, clients de langages variés RabbitMQ - AMQP et les exchanges sont faits pour ça
    SI Java, JMS imposé, serveur JEE ActiveMQ Artemis
    Broker déjà présent dans le SI celui qui est là : l'exploitation maîtrisée vaut mieux qu'un produit théoriquement meilleur
    Répartition de tâches longues, priorités, reprise unitaire l'un ou l'autre - les deux le font nativement
    Fan-out massif, rejeu, très gros débits ni l'un ni l'autre : c'est un besoin de log
    Existant JMS à faire évoluer Artemis, avant d'envisager une réécriture

    Le critère qui prime sur la comparaison de fonctionnalités

    Un broker est une infrastructure critique : il faut savoir le superviser, le mettre à jour, le sauvegarder et le restaurer. Introduire un second broker dans un SI qui en exploite déjà un ajoute une astreinte, une expertise et une surface de panne.

    Le produit déjà maîtrisé gagne presque toujours contre celui qui coche une case de plus.

    Ce qu'il faut superviser

    Métrique Ce qu'elle révèle
    Profondeur de file la métrique n°1 : elle monte = les consommateurs ne suivent plus
    Taux d'entrée / sortie le déséquilibre avant qu'il ne devienne une saturation
    Messages non acquittés traitements bloqués ou consommateurs figés
    Contenu de la DLQ / DLX des messages qui échouent sans que personne ne le sache
    Mémoire et disque du broker RabbitMQ applique un blocage des producteurs quand les seuils sont atteints
    Redélivrances un message toxique qui tourne en boucle

    Le blocage des producteurs

    Quand la mémoire ou le disque franchit son seuil, RabbitMQ bloque les producteurs au lieu de perdre des messages. Symptôme côté application : des publications qui se figent, sans erreur, sans timeout explicite. On cherche alors un problème applicatif alors que la cause est la saturation du broker.

    Questions typiques, réponses courtes

    « Différence entre RabbitMQ et ActiveMQ ? » Le modèle de routage. RabbitMQ interpose un exchange entre le producteur et les files : la distribution se décide par bindings, le producteur ignore qui écoute. ActiveMQ publie directement vers une destination et brille surtout comme implémentation JMS dans un SI Java. RabbitMQ est plus à l'aise en environnement polyglotte, ActiveMQ dans un existant Java.

    « À quoi sert un exchange ? » À découpler le producteur des destinataires. Il route selon la clé du message et les bindings - exactement (direct), par motif (topic), à tous (fanout) ou par en-têtes. Ajouter un consommateur revient à lier une nouvelle file, sans modifier le producteur.

    « Comment gère-t-on un message en échec ? » Redélivrance, puis Dead Letter Exchange au-delà d'un nombre de tentatives. Pour un réessai différé, une file intermédiaire avec TTL dont le DLX pointe vers la file de traitement donne un délai croissant sans planificateur.

    « Pourquoi une instance travaille et pas les autres ? » Presque toujours le prefetch : le broker a poussé d'avance un lot de messages vers un consommateur, qui les garde le temps de les traiter. Sur des traitements longs et inégaux, prefetch = 1 rétablit une répartition équitable, au prix du débit.

    « Comment être sûr qu'un message publié est bien arrivé ? » publisher confirms pour que le broker accuse réception, mandatory pour être averti si aucune file n'accepte le message, file durable et message persistant pour survivre à un redémarrage. Sans ces réglages, un message peut disparaître sans la moindre erreur.
