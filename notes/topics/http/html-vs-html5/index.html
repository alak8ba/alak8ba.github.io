    HTML vs HTML5 • ce qui change vraiment

    Contexte

    La question « quelle est la différence entre HTML et HTML5 ? » revient régulièrement. La réponse courte se limite souvent à trois balises sémantiques ; l'essentiel est ailleurs, et tient en une phrase :

    Réponse courte

    HTML 4 décrit un document. HTML5 décrit une application.

    HTML 4 (1999) sert à structurer du texte et des liens ; tout comportement riche passait par un plugin (Flash, Java applet, Silverlight). HTML5 (2014) intègre au navigateur le multimédia, le stockage local, le temps réel, le travail en arrière-plan et la gestion d'historique - donc rend possible la SPA sans plugin.

    Repères historiques

    Étape Année Ce qui la caractérise
    HTML 4.01 1999 basé sur SGML, DOCTYPE long avec DTD, présentation mélangée à la structure
    XHTML 1.0 2000 syntaxe XML stricte, une seule erreur casse la page
    XHTML 2.0 abandonné rupture de compatibilité refusée par les navigateurs
    HTML5 2014 recommandation W3C, plus de DTD, algorithme de parsing spécifié
    HTML Living Standard depuis WHATWG, plus de numéro de version : le standard évolue en continu

    La précision qui compte

    Il n'y aura pas de « HTML6 ». Depuis 2019, la référence est le HTML Living Standard du WHATWG, mis à jour en continu. Dire « HTML5 » aujourd'hui, c'est désigner par commodité l'ensemble « HTML moderne + APIs du navigateur ».

    1. Le DOCTYPE et le parsing

    <!-- HTML 4.01 : le DOCTYPE référence une DTD -->
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN"
  "http://www.w3.org/TR/html4/strict.dtd">

<!-- HTML5 : plus de DTD, il ne sert qu'à activer le mode standard -->
<!DOCTYPE html>

    Le changement de fond est invisible mais majeur : HTML5 spécifie l'algorithme de parsing et la gestion des erreurs. Avant, chaque navigateur récupérait le HTML mal formé à sa façon - d'où les écarts de rendu historiques. Depuis, deux navigateurs conformes construisent le même DOM à partir du même HTML cassé.

    Un DOCTYPE absent ou erroné fait basculer le navigateur en quirks mode : boîtes CSS calculées à l'ancienne, comportements de compatibilité IE. C'est une cause classique de « ça ne s'affiche pas pareil » sur une page legacy.

    2. Sémantique

    <!-- HTML 4 : tout est div, la structure n'est portée que par les classes -->
<div id="header">
  <div id="nav">...</div>
</div>
<div class="content">
  <div class="post">...</div>
</div>
<div id="footer">...</div>

<!-- HTML5 : la structure est dans les balises -->
<header>
  <nav>...</nav>
</header>
<main>
  <article>
    <section>...</section>
  </article>
  <aside>...</aside>
</main>
<footer>...</footer>

    Balises introduites : header, nav, main, section, article, aside, footer, figure / figcaption, time, mark, details / summary, dialog, template.

    Pourquoi ça compte, concrètement :

    • accessibilité - les lecteurs d'écran exposent des repères de navigation (landmarks) ; <main> permet le saut direct au contenu
    • SEO - la hiérarchie du document est explicite pour les moteurs
    • maintenance - la structure ne dépend plus d'une convention de nommage de classes

    Balises de présentation abandonnées : <font>, <center>, <big>, l'attribut align. La présentation passe entièrement par CSS.

    3. Formulaires

    <!-- HTML5 : validation, saisie adaptée et sémantique sans une ligne de JS -->
<form>
  <input type="email"    required placeholder="nom@exemple.fr">
  <input type="date"     min="2026-01-01" max="2026-12-31">
  <input type="number"   step="0.01" min="0">
  <input type="tel"      pattern="[0-9]{10}">
  <input type="search">
  <input type="url">
  <input type="color">
  <input type="range"    min="0" max="100">
  <input list="villes" name="ville">
  <datalist id="villes">
    <option value="Chambéry">
  </datalist>
  <progress value="70" max="100"></progress>
</form>

    Les gains : le clavier adapté sur mobile (tel, email), la validation native (required, pattern, min, max), les attributs autocomplete et novalidate, et la Constraint Validation API (checkValidity(), setCustomValidity()).

    La validation navigateur n'est pas de la sécurité

    Elle améliore l'expérience utilisateur, rien de plus : elle se contourne en trois secondes avec les outils de développement ou un appel curl. La validation serveur reste obligatoire - @Valid, Bean Validation, contraintes en base.

    4. Multimédia et graphisme natifs

    Besoin Avant HTML5 Avec HTML5
    Vidéo / audio plugin Flash <video>, <audio>, <source>, <track>
    Dessin bitmap Flash, applet <canvas> + API 2D
    Dessin vectoriel images SVG inline dans le DOM
    3D plugin WebGL sur canvas

    C'est ce point qui a rendu Flash obsolète : le navigateur lit une vidéo sans dépendance externe, donc sans la surface d'attaque et les problèmes de mobile associés.

    5. Les APIs JavaScript • ce qu'on range sous « HTML5 »

    Formellement, la plupart ne font pas partie de la spécification HTML : ce sont des standards voisins arrivés dans la même vague. En pratique, tout le monde les range sous l'étiquette HTML5.

    API Ce qu'elle apporte Usage typique
    Web Storage localStorage, sessionStorage préférences UI, brouillon de formulaire
    IndexedDB base de données transactionnelle côté client mode hors-ligne, gros volumes
    History API pushState, replaceState, popstate routing d'une SPA sans rechargement
    WebSocket canal bidirectionnel permanent chat, cotations, collaboration
    Server-Sent Events flux serveur → client, EventSource notifications, avancement d'un batch
    Web Workers exécution JS dans un thread séparé calcul lourd sans figer l'interface
    Fetch requêtes HTTP à base de promesses remplace XMLHttpRequest
    File / Drag & Drop FileReader, FormData upload, prévisualisation
    Geolocation position de l'utilisateur (avec accord) cartographie
    Service Worker + Cache proxy client, hors-ligne, PWA application installable
    Notifications, WebRTC, Media Devices notifications système, pair-à-pair, caméra visio, scan

    6. Stockage côté client • le tableau à connaître

    C'est la partie la plus souvent creusée, parce qu'elle touche à la sécurité.

    localStorage sessionStorage Cookie IndexedDB
    Durée de vie permanente jusqu'à suppression l'onglet est fermé → perdu Expires / Max-Age permanente
    Portée origine (protocole + domaine + port) onglet courant domaine + chemin origine
    Capacité ~5–10 Mo ~5–10 Mo ~4 Ko large (centaines de Mo)
    Envoyé au serveur non non oui, à chaque requête non
    Accessible en JS oui oui oui, sauf HttpOnly oui
    API synchrone (bloque le thread) synchrone document.cookie asynchrone, transactionnelle
    Structure chaînes clé/valeur chaînes clé/valeur chaîne objets, index, curseurs 
    // Web Storage ne stocke que des chaînes : sérialiser explicitement
localStorage.setItem('prefs', JSON.stringify({ theme: 'dark', lang: 'fr' }));
const prefs = JSON.parse(localStorage.getItem('prefs') ?? '{}');

sessionStorage.setItem('brouillon', texte);   // perdu à la fermeture de l'onglet

    Jamais de jeton d'authentification en localStorage

    localStorage est lisible par tout script exécuté dans la page, y compris un script injecté par une XSS ou une dépendance npm compromise. Un jeton volé là est rejouable jusqu'à son expiration.

    La bonne réponse : cookie HttpOnly + Secure + SameSite, éventuellement porté par un BFF. Le cookie n'est pas lisible en JS, et il est envoyé automatiquement - au prix d'une protection CSRF à mettre en place.

    → Cookie Security · SSO

    Autre conséquence du tableau : un cookie de 3 Ko part avec chaque requête, y compris les images et les fichiers statiques. Mettre des données volumineuses dans un cookie dégrade toutes les requêtes de l'application.

    7. Rendu côté client, rendu côté serveur

    HTML5 a permis de déplacer le rendu dans le navigateur. C'est un choix d'architecture, pas un progrès automatique.

    flowchart LR
    subgraph SSR
      R1[Requete] --> S1[Serveur genere le HTML]
      S1 --> B1[Page utilisable immediatement]
    end
    subgraph CSR
      R2[Requete] --> S2[Serveur renvoie un HTML vide + JS]
      S2 --> B2[Le JS construit le DOM puis appelle l API]
    end
    Rendu serveur (SSR) Rendu client (CSR / SPA)
    Premier affichage rapide dépend du téléchargement et de l'exécution du JS
    SEO naturel nécessite SSR, prerender ou hydratation
    Charge serveur plus élevée déportée sur le poste client
    Navigation interne aller-retour réseau instantanée, sans rechargement
    Complexité faible état client, routing, cache à gérer

    L'état de l'art réconcilie les deux : rendu serveur puis hydratation (Angular SSR, Nuxt, Next). → Angular SSR

    Le déroulé en trois temps

    1. La bascule de nature - HTML4 décrit un document, HTML5 fait du navigateur une plateforme d'exécution : plus besoin de plugin.
    2. Trois axes concrets - sémantique (accessibilité, SEO), formulaires et multimédia natifs, et le lot d'APIs : stockage, temps réel, workers, historique.
    3. Le point de sécurité - localStorage contre cookie HttpOnly : c'est là que la discussion devient réellement technique.

    Questions typiques, réponses courtes

    « Quelle est la différence entre HTML et HTML5 ? » HTML4 décrit un document, HTML5 décrit une application. HTML5 intègre au navigateur ce qui demandait un plugin : multimédia, dessin, stockage local, temps réel, travail en arrière-plan. Il ajoute une sémantique explicite, des formulaires validés nativement, et un algorithme de parsing spécifié qui met fin aux écarts entre navigateurs.

    « Trois apports concrets ? » Les balises sémantiques (header, nav, main, article) pour l'accessibilité et le SEO ; <video> et <canvas> qui rendent Flash inutile ; et les APIs de stockage et de temps réel - Web Storage, WebSocket, Server-Sent Events - qui rendent la SPA possible.

    « Différence entre localStorage et sessionStorage ? » La durée de vie et la portée : sessionStorage est limité à l'onglet et disparaît à sa fermeture, localStorage persiste et est partagé entre tous les onglets de la même origine. Les deux sont synchrones, limités à des chaînes, et jamais envoyés au serveur.

    « Et par rapport à un cookie ? » Le cookie est envoyé automatiquement à chaque requête vers le domaine - donc il pèse sur toutes les requêtes, mais il peut être HttpOnly, c'est-à-dire invisible au JavaScript. Web Storage offre beaucoup plus d'espace, n'alourdit aucune requête, mais reste lisible par tout script de la page.

    « Où stocker un jeton d'authentification ? » Pas dans le localStorage : toute XSS le récupère. Un cookie HttpOnly + Secure + SameSite, idéalement porté par un BFF ; à défaut, le jeton en mémoire seulement, perdu au rechargement. Le cookie impose en contrepartie une protection CSRF.

    « Le DOCTYPE sert encore à quelque chose ? » Oui : <!DOCTYPE html> ne référence plus de DTD, mais son absence fait basculer le navigateur en quirks mode, avec un calcul des boîtes CSS à l'ancienne. C'est une cause classique d'écart de rendu sur une page héritée.

    « La validation HTML5 dispense-t-elle de valider côté serveur ? » Non, jamais. Elle améliore l'expérience utilisateur et se contourne en trois secondes avec les outils de développement. La validation serveur reste la seule qui protège les données.
