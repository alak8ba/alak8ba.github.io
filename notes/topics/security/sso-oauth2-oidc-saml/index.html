    SSO • Single Sign-On (OAuth2, OIDC, SAML)

    Contexte

    Dans un système d'information d'entreprise, un utilisateur travaille sur plusieurs applications dans la même journée :

    • un ERP
    • un intranet
    • deux ou trois applications métier
    • des outils SaaS (messagerie, GED, ticketing)

    Sans mécanisme commun, chaque application gère ses propres comptes, ses propres mots de passe et sa propre politique de sécurité.

    Les conséquences sont connues :

    • multiplication des mots de passe, donc mots de passe faibles ou réutilisés
    • arrivée / départ d'un collaborateur à répercuter dans N applications
    • aucune vision centrale de « qui a accès à quoi »
    • MFA impossible à généraliser

    Le SSO (Single Sign-On) répond à ce problème : l'utilisateur s'authentifie une seule fois auprès d'un fournisseur d'identité, et les applications lui font confiance.

    Le point à ne pas confondre

    Le SSO est une propriété du système d'information : une seule authentification pour plusieurs applications.

    OAuth2, OIDC, SAML et Kerberos sont les protocoles qui permettent de l'obtenir.

    Le JWT n'est ni l'un ni l'autre : c'est un format de jeton, souvent utilisé par OIDC pour transporter l'identité.

    Vocabulaire

    Terme Signification
    Authentification qui est l'utilisateur (prouver son identité)
    Autorisation ce qu'il a le droit de faire (rôles, scopes, permissions)
    IdP - Identity Provider le système qui authentifie : Keycloak, Entra ID, Okta, ADFS, Ping
    SP - Service Provider l'application qui délègue l'authentification (vocabulaire SAML)
    RP - Relying Party même rôle que le SP, en vocabulaire OIDC
    Client l'application enregistrée auprès de l'IdP (vocabulaire OAuth2)
    Resource Server l'API qui valide le jeton pour protéger ses endpoints
    Assertion / Token la preuve signée émise par l'IdP et vérifiée par l'application
    Fédération faire confiance à un IdP externe (partenaire, client, annuaire d'un autre SI)

    Les trois familles de protocoles

    OAuth 2.0 OIDC (OpenID Connect) SAML 2.0
    Sert à autoriser un accès à une API authentifier un utilisateur authentifier un utilisateur
    Construit sur HTTP + JSON OAuth 2.0 (surcouche) XML + signatures XML-DSig
    Jeton access_token (souvent JWT) id_token (JWT obligatoire) assertion XML
    Transport header Authorization: Bearer idem + endpoint userinfo POST de formulaire, redirections
    Terrain typique API, mobile, machine-to-machine SPA, applications web modernes grands SI, ADFS, SaaS historique
    Découverte - /.well-known/openid-configuration fichier de métadonnées XML
    Verdict ne fait pas d'authentification à lui seul standard par défaut aujourd'hui encore très présent, à savoir lire

    Le piège classique

    « On fait de l'authentification en OAuth2 » est une phrase fausse. OAuth2 délègue une autorisation d'accès, il ne dit rien de l'identité de l'utilisateur. C'est OIDC, la surcouche, qui apporte l'id_token et donc l'authentification.

    Flux OIDC • Authorization Code + PKCE

    C'est le flux à connaître : celui recommandé aujourd'hui pour les applications web comme pour les SPA.

    sequenceDiagram
participant U as Utilisateur
participant APP as Application (RP)
participant IDP as Identity Provider
participant API as API (Resource Server)

U->>APP: accès à une page protégée
APP-->>U: redirect /authorize (client_id, redirect_uri, scope, state, code_challenge)
U->>IDP: authentification (mot de passe + MFA)
IDP-->>U: redirect vers redirect_uri avec un code
U->>APP: code d'autorisation
APP->>IDP: POST /token (code + code_verifier)
IDP-->>APP: id_token + access_token + refresh_token
APP->>API: GET /resource (Authorization: Bearer access_token)
API->>IDP: clés publiques JWKS (mises en cache)
API-->>APP: 200 OK

    Les points qui font la sécurité de ce flux :

    • le code d'autorisation transite par le navigateur, mais il est inutilisable seul
    • l'échange code → jetons se fait de serveur à serveur, hors du navigateur
    • PKCE (code_challenge / code_verifier) empêche l'interception du code par une autre application sur le poste
    • state protège contre le CSRF au retour de redirection
    • nonce lie l'id_token à la demande initiale

    Flux à ne plus utiliser

    • Implicit flow (response_type=token) : le jeton passe dans l'URL, il finit dans l'historique et les logs. Remplacé par Authorization Code + PKCE.
    • Resource Owner Password Credentials : l'application manipule le mot de passe de l'utilisateur, ce qui interdit MFA et SSO. Réservé à des cas de migration.
    • Client Credentials reste valide, mais uniquement pour du machine-to-machine (batch, service à service) - il n'y a pas d'utilisateur derrière.

    Les trois jetons, et à quoi ils servent

    Jeton Question à laquelle il répond Destinataire Ne jamais faire
    id_token qui est connecté l'application cliente l'envoyer à une API comme jeton d'accès
    access_token quels accès sont autorisés l'API (resource server) le stocker dans un endroit lisible par du JS non maîtrisé
    refresh_token obtenir un nouvel access_token l'IdP uniquement l'exposer au navigateur sans rotation

    Ordres de grandeur en production :

    • access_token : 5 à 15 minutes
    • id_token : durée courte, il ne sert qu'à établir la session applicative
    • refresh_token : heures à jours, avec rotation et révocation possible

    Ce que l'API doit valider

    Un resource server qui décode le JWT sans le vérifier n'authentifie rien. La validation minimale :

    1. signature vérifiée avec la clé publique de l'IdP (JWKS, kid, cache + rafraîchissement)
    2. iss - l'émetteur est bien l'IdP attendu
    3. aud - le jeton a été émis pour cette API, pas pour une autre
    4. exp / nbf - validité temporelle, avec une tolérance d'horloge de quelques secondes
    5. scope / rôles - autorisation effective sur l'endpoint appelé
    // Resource server : validation déléguée à Spring Security
@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(rolesConverter())))
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .csrf(csrf -> csrf.disable())   // légitime seulement si aucun cookie d'auth
            .build();
    }
}

  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://idp.exemple.fr/realms/interne
          audiences: facturation-api

    Besoin Starter Spring
    l'application fait le login et gère la session utilisateur spring-boot-starter-oauth2-client
    l'API valide un jeton reçu spring-boot-starter-oauth2-resource-server

    Le cas d'une SPA • deux options défendables

    Option 1 - jetons dans le navigateur

    La SPA porte le flux Authorization Code + PKCE et stocke les jetons côté client.

    • simple à mettre en place, pas de composant supplémentaire
    • toute faille XSS devient un vol de jeton : le localStorage est lisible par n'importe quel script chargé dans la page

    Option 2 - BFF (Backend For Frontend)

    Un backend maison porte le flux, garde les jetons côté serveur et n'expose au navigateur qu'un cookie de session HttpOnly, Secure, SameSite.

    • le jeton n'est jamais accessible au JavaScript
    • il faut alors se protéger du CSRF (jeton anti-CSRF, SameSite=Lax ou Strict)
    • c'est l'option retenue dès qu'il y a une exigence de sécurité forte

    La formulation qui résume le choix

    « Dans une SPA, on privilégie le pattern BFF : le flux OIDC est porté par le backend, le navigateur ne reçoit qu'un cookie HttpOnly. Le jeton reste hors de portée du JS, donc hors de portée d'une XSS. Le prix à payer, c'est un composant de plus et la protection CSRF à remettre en place. »

    Sessions et déconnexion • là où le SSO se complique

    Le SSO crée plusieurs sessions superposées :

    Session IdP        (cookie sur le domaine de l'IdP)
   ├── Session application A     (cookie ou jeton)
   ├── Session application B
   └── Session application C

    Se déconnecter de A ne déconnecte ni l'IdP, ni B, ni C. D'où :

    Mécanisme Effet
    Logout local détruit la session de l'application seule - l'utilisateur se reconnecte sans mot de passe
    RP-initiated logout (end_session_endpoint) ferme aussi la session IdP
    Front-channel logout l'IdP charge des iframes de déconnexion des autres applications (fragile, bloqué par les navigateurs)
    Back-channel logout l'IdP appelle une URL serveur de chaque application (fiable, à privilégier)
    SLO SAML équivalent côté SAML, historiquement peu fiable en pratique

    Un JWT ne se révoque pas

    Tant qu'il n'est pas expiré, un JWT signé reste valide : l'API n'interroge personne pour le vérifier. Trois réponses, à combiner :

    • durée de vie courte de l'access_token
    • révocation portée par le refresh_token côté IdP
    • introspection (/introspect) ou liste de révocation quand la coupure doit être immédiate - au prix d'un appel réseau par requête

    Kerberos et SSO Windows

    Dans un SI avec Active Directory, l'utilisateur est déjà authentifié par son poste. Le SSO « transparent » repose alors sur Kerberos via SPNEGO : le navigateur présente un ticket, aucun écran de login n'apparaît.

    En pratique aujourd'hui, on l'utilise en amont : Kerberos authentifie l'utilisateur auprès de l'IdP (Keycloak, ADFS), et l'IdP émet ensuite des jetons OIDC pour les applications. Les applications ne parlent que OIDC, jamais Kerberos.

    Rôles et autorisation

    L'authentification donne l'identité. Il reste à décider des droits.

    flowchart LR
    IDP[IdP : groupes et roles] -->|claims dans le jeton| API[API]
    API --> RBAC[Controle d acces applicatif]
    RBAC --> DEC{autorise ?}

    Deux stratégies, souvent combinées :

    • rôles portés par le jeton - rapide, aucun appel supplémentaire, mais un changement de droit n'est effectif qu'au renouvellement du jeton
    • rôles résolus par l'application - le jeton porte seulement l'identité, les droits fins sont lus en base à chaque requête

    Règle de conception : les rôles métier structurants dans l'IdP, les permissions fines dans l'application.

    Pièges rencontrés en production

    Piège Symptôme Correction
    aud non validée un jeton émis pour une autre application est accepté valider explicitement l'audience
    JWKS non mis en cache l'IdP est appelé à chaque requête : latence et point de rupture cache, rafraîchi sur kid inconnu
    Horloges désynchronisées 401 intermittents en cluster NTP + tolérance de quelques secondes
    redirect_uri en wildcard redirection vers un domaine contrôlé par un attaquant liste blanche exacte
    id_token utilisé comme jeton d'API fonctionne en recette, refusé par une gateway sérieuse envoyer l'access_token
    Session applicative plus longue que le jeton l'utilisateur reste « connecté » sans droits valides aligner les durées de vie
    Rôles dupliqués IdP / base applicative droits incohérents selon le chemin d'appel une seule source de vérité par type de droit

    Questions typiques, réponses courtes

    « Différence entre authentification et autorisation ? » L'authentification établit l'identité, l'autorisation établit les droits. Les deux sont séparées : un utilisateur correctement authentifié peut légitimement recevoir un 403.

    « OAuth2 ou OIDC ? » OIDC pour connecter un utilisateur, OAuth2 pour autoriser l'accès à une API. OIDC étant une surcouche d'OAuth2, on met en place OIDC et on obtient les deux.

    « SAML ou OIDC ? » OIDC pour tout ce qui est neuf : JSON, adapté au mobile et aux SPA, découverte automatique. SAML quand l'IdP ou le SaaS en face ne parle que SAML - ce qui reste fréquent dans les grands SI.

    « Où stocker le jeton dans une SPA ? » Idéalement nulle part côté navigateur : BFF et cookie HttpOnly. À défaut, en mémoire - jamais en localStorage si l'exposition XSS n'est pas maîtrisée.

    « Comment déconnecter un utilisateur immédiatement ? » La déconnexion applicative ne suffit pas : back-channel logout côté IdP, révocation du refresh_token, et l'access_token en cours reste valide jusqu'à expiration - d'où sa durée de vie courte.
